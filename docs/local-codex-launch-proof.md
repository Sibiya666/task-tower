# Локальный запуск обычной сессии Codex: проверенный первый шаг

Проверка начата 2026-11-05; операторский итог — 2026-11-06 (Europe/Moscow). Пользователь согласовал сначала доказать запуск из локального процесса Task Tower в нужном worktree, затем связывать его с Beads и кнопкой башни. Права, аккаунт, авторизация, установка и настройки модели не изменялись. Независимая приёмка и PR/main gates сохраняются.

## Что действительно запущено

Отдельный локальный Python-клиент, подготовленный как прототип точки запуска Task Tower, вызвал установленный `codex app-server --listen stdio://`. Он не использовал инструменты чата `create_thread`/`send_message_to_thread`, не требовал API key, нового OAuth flow или управляемого daemon. Прототип и приватные receipts сохранены в runtime и не входят в продукт. Это доказательство доступного интерфейса, а не поставленная кнопка или готовый dispatcher.

Установленный CLI: `0.166.0-alpha.6`, SHA256 `925c7d0665ffa49b0dcf748e034a805a04da984164ac92301432073b47789b99`. Worktree: `task-tower-local-launch`; ветка: `test/task-tower-local-launch`; начальная база: `e021e0c8c38f1ea9af6bf1860d2eedcff97edca1`. Прежние рабочие папки, ветки и claims не переносились и не перезаписывались.

Использован документированный протокол: `initialize` → `initialized` → `thread/start` с точным `cwd` → `turn/start`; затем `thread/resume` той же сессии для отдельной read-only проверки. Поля model, approvalPolicy, sandbox/permissions не переопределялись. [Официальная документация App Server](https://learn.chatgpt.com/docs/app-server) описывает локальный stdio transport, создание/возобновление threads, turns и события завершения. Фактическая поддержка этих операций проверена на установленном бинарнике; новые примеры документации не считаются измерением старой версии.

Оба model turns имеют реальные session/turn IDs и наблюдаются через Desktop API. Учётная запись обслуживалась установленным Codex; Task Tower не читал и не копировал секреты в brief. Подлинные warnings и отрицательный исход первой попытки сохранены в приватном runtime. Ни один запрос одобрения клиент не принимал автоматически.

Успешное завершение read-only хода не означает чистый startup: в его stderr сохранены 34 WARN и 6 ERROR, включая сбои запуска/авторизации optional MCP, timeout каталога моделей и plugin/cache/network ошибки. Их причины и Desktop plugin parity не квалифицированы; доступность всех tool routes не заявляется. Новая авторизация для исправления этих сообщений не выполнялась.

## Что можно строить на этом результате

Для тонкой связки достаточно небольшого клиента локального App Server: создавать/возобновлять thread, проверять cwd, передавать brief, сопоставлять request/thread/turn IDs, читать события и обрабатывать запросы оператора. Доступность механизма создания обычной сессии теперь измерена на данной Windows10.

Перед задачами на запись нужен отдельный проверяемый шаг: сопоставить существующий профиль Desktop и direct app-server, выбранную пользователем модель, разрешённые каталоги и поведение approval. Нельзя молча выдать read-only default за writable Desktop-сессию, автоматически одобрить запрос или расширить права, чтобы опыт прошёл. Этот отчёт не выбирает новый профиль.

Beads claim/heartbeat, tower UI, постоянный dispatcher, общий lifecycle/cancellation controller и автоматическая PR/main интеграция здесь не добавлялись. G1/G2 полной автономии и PR85 не квалифицированы. Сначала требуется независимая приёмка этого фактического результата; дальнейшая связка использует действующие admission и exact head/base/main gates, а не новую очередь.
