# Слияние PR как событие Task Tower

Workflow [Task Tower postmerge](../.github/workflows/postmerge.yml) слушает `pull_request.closed` для main и выполняет работу только при `merged=true`. Проверяет точный merge commit на Windows/macOS/Linux и публикует по одному JSON artifact для каждой платформы. Тестовый провал публикуется как failed и оставляет job красным.

Связь задаётся в описании PR отдельной строкой:

```text
Task-Tower: TT-BOOTSTRAP-001
```

Несколько задач — несколько таких строк. Без маркера artifact содержит пустой task_ids: автоматического угадывания по названию нет. Содержимое PR не исполняется как shell-код; используется parser JSON. Workflow имеет только contents:read и не меняет main или карточку задачи.

Событие содержит repository, номер PR, merge SHA, task IDs, платформу, результат CI, ссылку на Actions run и delivery key с учётом повторной попытки. Это входной контракт будущего сервиса очереди. Событие passed означает успешные автоматические тесты одной платформы, а не независимую финальную приёмку. Для кроссплатформенной задачи нужно собрать все обязательные результаты.

Этот hook работает на стороне GitHub после установки workflow в репозиторий. [Локальный postmerge worker](postmerge-worker.md) получает artifacts опросом API, запускает отдельного приёмщика и обновляет карточку. Публичный webhook endpoint на компьютере не нужен. Состояние и повторная доставка сохраняются в SQLite; новая попытка CI имеет новый delivery key, повторное ревью task+SHA требует явного retry. Интерфейс книг и облачная синхронизация локальных карточек остаются отдельными этапами.

Целевой цикл: merge → postmerge pending → проверки → агент-приёмщик → done либо возврат. Механизм не заменяет отдельного приёмщика и не снимает барьер очереди слияний. PR#2 уже был влит до добавления hook: ретроактивного запуска нет. Его фактическая postmerge-проверка сохранена в карточке как заблокированная из-за stale evidence.

## Почему приёмку нельзя молча перехешировать

Пилот обнаружил смену LF/CRLF при checkout и смешанные окончания строк до коммита (LF внутри, CRLF в конце). Исходные хеши удалось точно восстановить из тех же Git blob, меняя только окончания строк; содержательной правки не было. Новые текстовые приёмки используют явную схему нормализации UTF8/CRLF; legacy остаётся строгим raw hash. Содержательные изменения всё ещё дают stale. Старые блокировки снимаются только повторным независимым принятием актуального результата; ни событие merge, ни успешный CI не обновляют эти хеши автоматически.

## Ограничения событий GitHub

GitHub Actions обычно не запускает closed/push workflow, если породившее событие действие выполнено стандартным GITHUB_TOKEN другого workflow. Будущему автоматическому merge-controller нужны подходящий App/dispatch путь или сверка состояния main. Отдельно учитываются потерянные события и PR без привязки к задаче. [Документация GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
