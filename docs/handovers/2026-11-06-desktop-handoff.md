## Одна каноническая база, без второй очереди

Сначала прочитать [AGENTS](../../AGENTS.md), [единую спецификацию](../superpowers/specs/2026-11-05-task-tower-unified-design.md), [backlog](../backlog.md) и эту инструкцию.

Если другой desktop — другая сессия на том же компьютере и существующий канонический Beads доступен, использовать **его**. Восстанавливать рядом ещё одну рабочую очередь не нужно. Проверить фактический backend/project identity и native `show/history`; архив остаётся резервной копией.

На другом Windows-компьютере:

1. Получить эту ветку и приватный ZIP. Сверить его SHA256 до распаковки. Git и Python 3.11+ должны уже быть доступны; автоматически устанавливать инструменты или менять аккаунт/модель/авторизацию/ACL нельзя.
2. Распаковать ZIP в приватную папку, прочитать `RESTORE.md`, `MANIFEST.json` и `restore_beads.py`. Использовать исходники Task Tower из этой транспортной ветки: хеши доверенных process helpers проверяются скриптом.
3. Выполнить с фактическими новыми путями:

   ```text
   python restore_beads.py --repo <checkout-TaskTower> --target <НОВАЯ-приватная-папка-Beads>
   ```

   Target **не должен существовать**. Скрипт создаёт отдельный Git root без remote/hooks, проверяет фактический `bd where` и пустую базу до restore. `--force` ограничен только этой новой пустой базой. Существующая база не перезаписывается. Все операции ограничены, вывод приватный; при ошибке сохранить target/receipts и разбирать неизвестный исход, не переинициализировать и не повторять эффект вслепую.
4. Проверить реальный `RESTORE_VERIFIED.json` в соседней папке receipts, 46/323, project identity, Dolt root и фактические native-запросы. Старая база остаётся paused/standby. После проверки использовать **только восстановленную** как канонический источник; одновременно возобновлять запись на двух компьютерах нельзя. Это разовый перенос, не реализация multi-machine sync/VPS/HTTP.
5. Сохранённый snapshot служит сравнением данных, а не разрешением исполнения. Перед эффектами заново прочитать native task/owner/history/dependencies/fences. Не менять владельцев чужих карточек и не реконструировать исполняемое состояние из JSON.

Существующие legacy runtime/unknown-effect fences на исходной машине сохраняются как инертная история. Они не превращены в импортированные задания и не разрешают replay старого conveyor. Новые machine-local display пути настраивать по [документации Books](../local-beads-books.md); Books остаётся read-only, его конфиг не выдаёт execution rights.

## Как продолжить исходную работу

Сначала восстановить/выбрать единственный настоящий канонический Beads, сверить актуальные GitHub/main/PR и разрешения. При явном продолжении пользователем проверить причину паузы, исходного owner и все закрытые зависимости `tt-e4n.6`, затем возобновить эту карточку guarded native update без смены владельца и без replay.

Для разработки взять отдельную чистую ветку/worktree от свежего **принятого** main и перенести **только WIP-коммит `da869a52409993de06d71670a8c7e0d8f107a851`**. Это позволяет применить обычный cherry-pick/разрешение конфликтов, сохранив новые изменения main. Не заменять целиком README старой копией поверх изменившегося main; не сливать транспортную документацию вместе с аналитической поставкой. Сохранить эту ветку и приватные receipts.

Завершить самодостаточный отчёт: все пять HE01 подсистем, HE02–05, все H2 R0–R8/P0–P4, четыре canonical-критерия, точные уточнения существующих карточек, полные proposal/negative/metric/cost/rollback/auth контракты. Перепроверить ссылки и факты новым реальным исполнением проверок с честными новыми идентичностями. Затем отдельные независимые DEV и TEST, свежая whole-PR приёмка **head и base**, genuine `task-tower/pr-acceptance`, весь применимый CI, protected expected-head merge, exact-main CI/actual artifact и независимая postmerge-приёмка; только после этого canonical close/readback и синхронизация Issue57. Changed H/B аннулирует verdict; failed/missing/cancelled CI не считается успехом.

Принятые Books/overlay/admission/CI сохраняются. Обязательные шесть ролей уже заменены составом по задаче, независимость проверки остаётся. Не строить второй task engine, не возрождать старый pipeline, не менять модель/аккаунт/auth/ACL/установки и не квалифицировать другую платформу неявно. Новая машина и передача Beads не доказывают G1/G2 или пригодность Windows executor B. Сначала конкретный B, затем полезный C до настоящей книги по согласованной спецификации.
