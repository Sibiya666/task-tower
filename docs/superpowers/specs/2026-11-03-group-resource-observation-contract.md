# Task4R concrete resource-observation contract

This implementation proposal refines the accepted R3 observation boundary. It does not admit registered group execution or replace the resource/owner/component transaction, workspace/epoch gates, installed pilot or final acceptance. Code changes below this boundary require fresh independent specification acceptance before activation.

## Genuine policy and observation ownership

Use a fixed host-owned resource context derived only from the existing actual `RegistrationContext`: revalidate its held source files, real private loaders, same pinned existing J and actual committed capacity epoch. A caller's normalized dictionary, policy hash, observation digest or capability Boolean cannot construct execution authority. Preserve installation identity, complete grant/profile/pool authority and explicit count/resource minima; source/authorization drift refuses rather than being treated as a capacity-only change.

`observe_host` consumes that genuine context and an absolute monotonic deadline, collects in the same eventual claiming process within the lesser of two seconds and the remaining caller budget, and returns the specified closed version1 observation body. Collection grants no reservation. The fixed claim implementation must collect or resolve only a corresponding private process-local observation, then revalidate the same actual policy/epoch, collector PID, clock and age inside the existing J transaction. It must recompute held leases and every count/pool/group/component/owner condition there. No public sample-insertion API or SQL-history-to-current-sample path is added.

Keep an immutable canonical copy of a genuinely collected observation in a bounded private process-local registry (at most32 unexpired entries). Returning or modifying the public observation dictionary does not modify that copy. The registry is not a second task/resource journal: J remains the only durable reservation authority. A digest only locates a genuine local entry; it never authenticates imported JSON. SQL observation rows are audit history only and cannot restore that registry after a crash.

## Collector lifetime and clock binding

The existing `boot_id` wire/SQL field identifies a collector lifetime that cannot span an OS boot, rather than claiming an OS-supplied boot UUID. Generate a private random UUID for each actual collector process lifetime and bind it together with the actual PID and initial monotonic reading. Reject PID changes/fork inheritance, backward monotonic or wall-clock movement and mismatched lifetime. A new process, even with a recycled PID, has an empty registry and a fresh lifetime UUID; after an OS reboot no prior process-local observation survives. Do not infer a current sample from a persisted PID/UUID or label this an operating-system boot identifier. This is deliberately stricter than cross-process reuse of a boot-wide observation and needs no new native probe.

The actual sample is valid for at most five seconds from collection start. Expiry is capped by the caller's original deadline, never renewed by reading or entering a transaction. Collection deadline checks occur before and after each native call. A slow/failed probe yields unavailable capabilities; no stale positive sample is installed. Recheck monotonic expiry and collector lifetime after any SQLite wait and immediately before committing a claim. A stored observation alone grants no claim after restart.

## Windows supported and unknown capabilities

Use only the already enumerated read-only native APIs: `GetActiveProcessorCount`, `GetProcessAffinityMask`, `GlobalMemoryStatusEx`, `IsProcessInJob` and `QueryInformationJobObject`, plus the current-process pseudo-handle needed by those calls. No shell, WMI, provider/account query, registry probe, optional dependency, installation or permission change is needed.

On a supported single processor-group observation, CPU is the conservative intersection of active system processors and the actual nonzero process affinity mask. An invalid/empty mask or a machine beyond the native mask's supported processor-group representation makes CPU unknown; do not substitute environment variables or `os.cpu_count`. Memory is a conservative usable available-memory measurement from `GlobalMemoryStatusEx`, bounded by the reported available physical, virtual and commit values. API failure or inconsistent sizes makes that capability unknown.

`IsProcessInJob(NULL job)` determines membership in any job. If membership cannot be established, CPU and memory constraint capability are unknown. When inside a job, `QueryInformationJobObject(NULL, ...)` exposes only the immediate job; it cannot establish the whole parent chain. Query the immediate supported CPU/memory limit information for provenance, but keep the affected resource capabilities unknown while complete enclosing constraints are unresolved. A zero immediate limit flag is not proof of an unconstrained parent. No breakaway or altered sandbox is attempted to make a probe pass. This conservative case may need an already explicitly installed fallback; the implementation does not add one.

This follows Microsoft's documented [nested-job query behavior](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject), [any-job membership query](https://learn.microsoft.com/en-us/windows/win32/api/jobapi/nf-jobapi-isprocessinjob), [processor-group affinity limits](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessaffinitymask) and [volatile available-memory observation](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex). Native Linux/macOS collectors remain deferred to #61; portable schema/arithmetic tests and three-platform CI remain required.

## Arithmetic and verification

Preserve R3 exactly: one logical CPU/1GiB headroom, maximum CPU and memory across all six explicitly granted role profiles plus100 CPU millis/64MiB helper overhead, all held leases subtracted, unknown held estimates blocking every fresh claim, checked signed64 arithmetic, minimum explicit count/resource/pool caps and fallback only for unavailable measurements. Fallback never raises a known value or supplies a missing/revoked harness grant. No minimum-one or maximum-two is synthesized. Product/component reservations and active resource leases remain separate; positive cleanup alone can release an action envelope, never PID disappearance.

Tests must distinguish pure arithmetic/shape consistency from genuine observations and atomic claims. Cover actual same-process collection, changed public dictionaries/imported JSON, stale/foreign/restarted/clock/epoch samples, native failures and nested-job unknowns, explicit fallback, capacity debt, competing claims and legacy omitted-G bypass. Actual three-process overlap and installed three-task/six-role evidence remain mandatory later; arithmetic over three fixture estimates does not satisfy them. Do not lift registered execution while Task5 workspace/current-epoch producers remain unavailable.
