# Task4R/5 first producer: genuine queued group admission

This proposal binds the next implementation step to the actual accepted journal, group binding and registration producers. It does not enable resource claims, clones or roles. The already accepted resource-observation foundation remains read-only; every registered execution path stays closed until its real transactional consumer and workspace/current-epoch producer are independently accepted together.

## Actual producer, unchanged storage

Add a narrow `PipelineJournal.submit_group(request, *, context)` for metadata admission only. context must be the actual existing `RegistrationContext`, owned by this same journal object and pinned existing file, with freshly revalidated real G/P/E/C loaders and actual committed installation/current policy/capacity epoch. A dictionary, hash, route label, caller group_id or implementation flag is not accepted as context. The source request retains the existing closed dispatcher version1 identity fields and validation.

Resolve the requested repository/Issue/task/runner through the actual private policy and `group_policy.group_binding`, including original task/profile/roles/pins/scope/budgets. Missing or ambiguous private routing refuses. This is a queued locator, not execution authority: no GitHub issue data, model output or declared completed artifact substitutes for later genuine source/graph/admission checks.

Keep the original six run-table schema and values. A new queued run has the same ordinary initial state as existing submit: stage spec, generation1, owner/PID/deadline/admission/source/base/checkpoint/manifest/input absent, zero original counters, host-selected run/branch identity and the original private limits/profile policy binding. Insert its group_runs companion in the same BEGIN IMMEDIATE: run_kind group, actual private group_id and authorization digest, exact original group_binding JSON/digest, isolation unprepared, first_eligible_sequence/current_base_epoch null. No reservation, action, resource observation/lease, source resolution or epoch is created. First-eligible sequence belongs to later actual graph-ready scheduling, not queue insertion.

Reuse the existing journal receipt representation; it proves only accepted queue identity. Preserve the original request/delivery/run IDs and lookup behavior. Repeated delivery returns its original matching identity without changing its binding, counters or run kind. An existing legacy row is never converted to group by resubmission. A different delivery for an already admitted Issue refuses. No dispatcher backend mapping, unknown delivery or historical receipt is rewritten or replayed.

## Explicit event domains and offline consistency

No DDL/table/index change is required. Existing registration binding/capacity events are global and have run_id null. A queued group binding event uses existing kind binding with its actual nonnull run_id and a closed body exactly {version,binding_kind,run_id,delivery_id,capacity_epoch,binding,binding_sha256}, version1/binding_kind queued_group. That tag describes metadata only; it cannot select a runnable implementation. The SQL run_kind plus genuine producer/current private context, not an imported tag, determines all later consumers.

Narrow registration validation to its global null-run event domain while retaining every existing strict field/provenance/epoch/adoption check. Validate every new per-run binding event against its actual queued run, exact saved binding/digest and corresponding saved registration epoch. Existing group event validation must not silently skip unvalidated nonnull binding events. Keep the current legacy migration/adoption/history/fence/release validation unchanged over the legacy subset; every new group row is separately exhaustively validated. Reject missing/duplicate/orphan/foreign or inconsistent binding rows/events and any executable state/action/reservation/epoch on this queue-only path.

Offline validation checks exact field/type/identity/scope/budget formats and saved registration/role/profile/task relations without reading revoked executable or instruction files. Stored consistency is not permission: the later execution consumer must recompute the genuine private binding, validate immutable authorization and current capacity separately, collect current graph/source/resource observations and claim atomically. A self-consistent imported SQL/JSON record never starts a process. Status/cancel/inspect remain metadata operations.

## Activation and proof boundary

Do not route ordinary installed adapter submissions through this new producer until the corresponding actual runtime consumer is supported. Existing raw registered-J legacy submit/claim paths remain refused rather than falling through old numeric limits. A future explicit host adapter may derive only the already registered G locator plus actual CLI-supplied P/E/C paths; never guess neighbors. Metadata lookup preserves known identities under execution-policy revocation.

Tests must use actual source loaders, migrated existing SQLite and real registration. Prove queue insertion/lookup/idempotency, private route/profile rejection, preserved original six-table rows/history/delivery IDs, transactional rollback on invalid input, orphan/extra/self-consistent metadata refusal, no actions/leases/reservations/epochs and continued registered execution closure. No manual SQL fixture may manufacture a runnable group/epoch/contribution to obtain a positive execution test.

The next resource/workspace step is coupled: actual authenticated source/graph admission and a fresh same-process sample must produce the first immutable preparation input and owner/deadline/resource/component claim; only an independently accepted real standalone-clone/current-epoch consumer can use it. No accepting generic group-intent setter, boolean capability switch or caller sample supplier is introduced by this queue metadata proposal. Live capacity-only epoch transitions, fair action completion/cleanup and legacy omitted-G bypass checks retain their remaining Task4R requirements.
