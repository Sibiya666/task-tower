## Purpose and decisions

An installation explicitly assigns authorized tasks to project groups and roles, runs independent work within shared capacity, and refills available slots without an active chat. Waiting tasks expose routing, dependency, capacity and ownership reasons. The user delegated routine technical choices; choices in this document are the author's rulings, not additional user commitments.

Python 3.11+ standard library only; Windows, macOS and Linux. Default installation capacity is 2 active tasks; configurable range is 1..2 in this release. Each group defaults to 1 active task, configurable 1..2 and never above installation capacity. These are task reservations, not the dispatcher's eight-delivery budget or permanent role processes. Six fresh executor/reviewer roles remain Issue16's stage protocol. Group roles describe who may fill those roles; they do not bypass independent acceptance.

Goals: explicit private routing, project/group fairness, verified dependency and parent-result gates, atomic local ownership/capacity, real background refill, safe same-repository independent development and repository-wide integration fencing. Anti-goals: inferred group assignments, a second stage engine, manually editable proof booleans, deadline-based owner stealing, weakened Git-ref checks, copied SQLite as distributed locking, or a milestone/fixture presented as night readiness. No hidden tool installation, model selection, credential scope grant or service registration. Worktrees/clones are not OS or credential sandboxes.

Three approaches considered: (a) keep Issue16's repository serialization, which cannot deliver parallel independent groups in one project; (b) suppress unrelated refs in its guard, which hides mutations and is rejected; (c) new runs use fully independent Git directories while retaining the complete ref guard. Choose (c), with conservative serialization for existing linked-worktree runs. Build on Issue16's accepted controller rather than duplicate its journal/watch loop. Distributed ownership remains #19; supervisor/watchdog and main recovery remain #25/#26.

## Private group policy

Add an optional private `--groups-config G` to pipeline adapter/work/watch/status; absence retains v1 behavior for ungrouped runs only. A group-bound journal run cannot execute through an omitted-config legacy path. Status/cancel/inspect still function after policy/profile revocation. G is strict UTF-8 JSON with duplicate/extra keys rejected and the same absolute, outside-checkout, alias/sidecar protections as pipeline policy. G never contains secrets or model names. Version 1 has exactly `version`, `installation_id`, `canonical_journal`, `max_active`, `projects`; max_active defaults to 2 if omitted (the only optional top-level field). installation_id is an installation-owned UUID and canonical_journal is the one approved absolute pipeline journal path. All group commands require their --journal to identify that same physical path, with aliases rejected; v2 journal metadata binds that installation_id and canonical G path before any group claim. An existing binding cannot be replaced by another G/installation or journal path. A project row requires `repository`, `groups`, `routes`, `aggregates` and permits only the optional `base_update`, `accepted_main_sources` fields defined below. Repository matches one existing private connection. Cross-project identities are always `owner/repository#issue`, case-normalized repository plus immutable GitHub Issue ID on admission.

Group row: exactly `{id, capacity, components, role_profiles}`; capacity optional default 1, all other fields required. IDs/components use Issue16 NAME syntax; `*` only as the sole component. Group IDs are unique within repository. `role_profiles` has exactly six keys: `spec_executor`, `spec_reviewer`, `development_executor`, `development_reviewer`, `test_executor`, `test_reviewer`, each naming an existing validated executor profile for that same repository/runner and same checkout/source authority. Reusing an executable/profile is permitted; executing and reviewing a contribution always requires different fresh process/instance IDs, and a contributor cannot approve its own downstream result. Do not invent persistent agents or a group coordinator model. Role routing may narrow allowed roles/paths/checks but never broadens the executor allowlist, source authority, publication mapping, budgets or pinned Superpowers instructions. The optional accepted_main_sources installation grant below is the only explicit derived initial-source extension; roles cannot infer it. Effective time/process/log limits are the minimum of existing applicable limits. No new token/dollar budget promise.

Route row: exactly `{issue, task_id, group}`; issue positive integer, task_id existing authorized task binding, group one project group ID. Use explicit identity routes, no prose/label/path heuristic and no wildcard fallback. A route need not cover every allowlisted task. Missing or ambiguous route parks only that task as `needs_input/routing_missing` or `routing_ambiguous`; it is visible even before dispatcher delivery, without fabricating or consuming a delivery. Invalid global schema stops configuration use, while an uncovered valid task does not stop other routes. In this release every bound role profile must equal that routed task's existing pipeline executor_profile: explicit six-role assignment means six fresh role instances using authorized execution authority, not permission to substitute a different executable/profile. Groups serving differently authorized tasks must be configured separately. This avoids widening Issue15/16's single task/profile allowlist through group policy. Task policy components must be a subset of group components (a group `*` permits any declaration, but a task `*` requires group `*`). Components are repository-scoped; equal strings in different repositories do not conflict. Coupled behavior uses an overlapping component or `*`; files merely being isolated is insufficient proof of independence. All current Issue16 allowed-path rules remain enforced.

Project rows additionally permit optional `base_update`, exactly `{enabled,max_updates}` with defaults `{enabled:false,max_updates:0}`. enabled is Boolean; max_updates is an integer 0..2, zero iff disabled. This installation-owned grant permits only the bounded trusted-base import below; absent/disabled grants yield `needs_input/base_update_disabled` after drift. Issue/model hints cannot enable it. Grant changes are authorization changes, never capacity-only changes. It is not a permission to resolve overlaps/conflicts, rewrite original authority or import unaccepted main.

Projects also permit optional `accepted_main_sources`, default empty list. Each row has exactly `{executor_profile,profile_sha256,anchor_sha}`: an existing same-repository profile ID, its exact validated full fingerprint and an explicitly installed accepted main anchor SHA. Duplicate profile bindings are invalid. This is the ONLY opt-in grant to resolve initial group source from authenticated accepted remote main instead of that profile's fixed local source_ref; no Issue/model hint, remote ref-shaped string or old profile implicitly grants it. Preserve the original profile bytes/fingerprint/executable/pins/allowlist/paths/budgets and record original configured source_ref alongside the derived source. Changes revoke continuation and require fresh explicit installation policy, not an in-run rewrite. Absence retains pinned-source behavior and honestly parks stale pinned sources rather than claiming automatic refill.

Group metadata, titles, prompts and model results are untrusted input; only private policy grants route/role/execution authority. Admission binds policy provenance, route/group, effective budgets, components and role pins. Reload/revalidate before each effect. Effective installation capacity is min(groups max_active, existing pipeline max_active); a group is additionally capped by that effective installation limit. A groups file cannot raise a stricter pipeline limit. A running task cannot be silently moved to another group/profile, given a fresh budget or new scope. Authorization drift parks after confirmed cleanup or fences unknown work. Capacity-only changes are the explicit exception: record a new capacity epoch after fresh private-policy validation; retain the run's original route/role/scope/budget binding and compare its authorization digest excluding only capacity fields. Apply capacity to new claims without resetting active run authority/deadlines. Restart a watch after changing policy; it must not silently hot-reload authority. Explicit reauthorization is a future audited operator action; this release does not unpark uncertain runs by editing JSON. Reducing a capacity below existing reservations blocks new admission and reports `capacity_debt`; it neither kills existing owners nor hides them.

## Graph, accepted dependencies and parents

Use native Issues/sub-issues and milestones without conflating them. Build a bounded repository-qualified graph from a fresh host snapshot, preserving unavailable/partial relations. Edges have distinct types: `requires_result` from existing blocked_by / blocked_by_task_ids resolution, `contains` from native parent/sub-issue relationships, and `aggregate_requires` from explicit private parent policy. Task-ID dependency resolution is unique within its project; unresolved/duplicate IDs block visibly. Explicit cross-project Issue references require an already connected readable source, not execution authorization for that other project. Do not infer an edge merely from a milestone or parent link.

An aggregate row has exactly `{issue, task_id, required_children}`; it must have its own task allowlist/pipeline policy/route. `required_children` is a nonempty unique list of repository-qualified references, each required to appear in that parent's current native sub-issues. Other native children remain visible but do not silently become mandatory; newly added or removed required relations invalidate the criteria. Parent policy grants no authority to execute a child. Parent integration starts only after every required child's `verified_done` result, followed by the parent's own independently accepted spec/development/test, exact-main CI/postmerge and publisher-driven closure. Merely closing all children or an aggregate parent Issue proves nothing.

Containment is NOT an execution dependency: a child can run while its parent awaits children. No automatic child-to-parent wait edge is added. Cycle detection includes explicit requires_result and aggregate_requires edges; it excludes contains edges. Thus a parent requiring a child plus that child explicitly requiring the parent is a genuine cycle; an ordinary hierarchy is not. Find strongly connected components deterministically; mark every cyclic member `dependency_cycle`, retain sorted involved identities/edge kinds, and mark downstream consumers `dependency_blocked`. Unavailable graph segments are `dependency_unavailable`, never treated as acyclic/ready. Bound each refresh to at most 1000 nodes / 10000 edges and existing bounded page readers; overflow is visible `graph_limit`, not truncation-to-ready.

Production readiness calls the genuine `verified_done` verifier through existing source factories for every required dependency, never injected true-returning predicates. Persist the verified receipt identity/digest, accepted main commit, Issue ID and source snapshot digest as an observation; cache only within one bounded refresh. Revalidate dependencies and immutable criteria before each launch/effect using Issue16 continuation checks plus the graph gate. A revoked/rejected/unavailable proof stops dependent work safely. Distinguish not yet accepted (`dependency_pending`) from unreadable (`dependency_unavailable`). A closed Issue without a verifiable accepted receipt is pending/unproven, not completed. Persist observations/reasons; observers never write a stage verdict.

## One local scheduling authority and fairness

There is one canonical pipeline journal per installation, identified by the installation-owned G path/UUID/canonical_journal binding above. Group/global reservations, action claims, component ownership and scheduling cursor updates occur in one `BEGIN IMMEDIATE` transaction in that SAME database. Bind installation metadata in that transaction before the first group claim; no external registry or second claim database is introduced. A crash before commit binds nothing; after commit the durable binding cannot be replaced. Do not place group claims in a second SQLite journal or claim cross-database atomicity. All execution claim paths in a G-bound canonical journal, including legacy rows and public work calls omitting G, enforce the persisted validated min(group-policy global maximum, pipeline maximum) capacity epoch and debt rules. Omitting G cannot raise the installation limit or add a reservation while capacity is exhausted; already reserved continuations follow the existing debt rules. Status, cancellation and read-only inspection remain available without valid executable/instruction pins. The dispatcher DB remains only a delivery journal; pipeline owns execution after its idempotent admission. A command trying another --journal with the same installation policy is refused before admission; omission of G cannot operate group-bound rows. Independently copied/modified G files and DBs are separate installations, not a supported shared-authority mechanism; this release cannot prove exclusivity against those or an uncooperative host. Multiple installations/hosts must not execute the same tasks before #19 provides distributed fencing. Private installation policy must declare disjoint execution scope if running independent installations.

Extend journal schema additively with validated group bindings, reservations, action claims, graph observations, fair cursors and integration observations. Existing run/attempt/effect/stage identities remain unchanged. Unique active run per repository/Issue and unique action owner per run remain database-enforced. A task reservation begins at first safe claim, binds stable run/branch/workspace identity and counts globally/per group. Active preparation/roles/checks/publication, clean ready boundaries and awaiting PR/main acceptance retain task reservations. A bounded worker completing one action is not task completion and does not release that reservation. `ready_for_pr` with disabled publication is a parked policy action: after positive cleanup it may yield execution capacity, but run and conflicting product ownership remain visible. Clean needs_input/cancelled yields execution capacity; unknown retains capacity AND conflicting ownership. Existing legacy active runs count toward global capacity and their conservative repository exclusion; they are not ignored for lacking a group row.

Do not release component ownership on transient role completion or a clean parked task that still owns unintegrated product changes; unrelated components/projects can continue. Releasing ownership requires accepted final integration or explicit authorized abandonment with positive cleanup, not a new run ID. Cancellation stops children through existing containment, records outcome and releases capacity only with positive cleanup proof and no unresolved attempt/effect. PID absence alone is not cleanup proof. No lease expiry or heartbeat timeout steals a run. Dead owners can hand off only at Issue16's existing proven safe-ready boundary, preserving stages/generation/deadline/counts. Unresolved launch, push, PR POST, Git preparation or cleanup remains fenced; inspect is read-only. Preserve old rejection histories and unknowns across restart.

For each dispatchable action, rotate projects in durable round robin, then eligible groups in that project, then tasks by first-eligible sequence and repository/Issue tie-break. A positively completed action advances cursors in its completion transaction, including a failed/needs_input role with proven cleanup; unknown actions do not advance them and remain excluded/fenced, so they cannot monopolize ordering. Claims record the selected turn but do not advance cursors. One worker performs at most one action before another claim. Continuations with held reservations may compete even when global capacity is full; new tasks must acquire both group/global capacity and components atomically. No preemption of running model processes. Blocked/full/conflicting groups are skipped; they do not monopolize a cursor or consume workers. Once finitely many eligible groups/actions remain and each action finishes within its budget, each gets a turn. This is fair action scheduling, not a deadline/SLA or a promise that a long-lived reservation permits an unlimited new task. Explain capacity wait separately from action/repository fencing. The parent gate consumes no execution slot before readiness.

The watch controller reuses Issue16's contained helper model, source backoff, one-controller lock, cancellation and health. It launches no more worker helpers than installation capacity; worker claims are the authoritative admission point, not watch's in-memory prediction. A freed reservation is refilled on the next bounded watch tick without chat or model coordination. Source failures park only affected projects; slow source helpers remain cancellable. A real running host watch process is required; no OS service or persistent startup is installed by this Issue.

## Workspace isolation without weakening Git guards

New group-managed runs get `<private runs_dir>/<run_id>/repository/` as a standalone clone and a stable `pipeline/<run_id>` branch. That checkout is the task worktree in user-facing terminology; `.git` is an independent directory. Clone from the already authorized source checkout with Git's no-local/no-hardlink copying, with hooks disabled, no shared object alternates, no shared git/common dirs, and no copied credentials. Validate all physical paths, devices/inodes/hardlinks/reparse points using existing guards. Reject object alternates, worktree common-dir sharing, submodules and unsafe paths. Record a clone-creation intent before creating directories/ref effects; observe exact source commit, expected clean checkout and remote mapping before marking complete. Partial creation/unknown outcome never causes delete/reclone/replay.

Set origin only to the existing verified connected remote, with push URL independently checked; no inherited local checkout origin may authorize a different repo. Use existing filtered Git environment and process containment, fixed argv and bounded deadlines; no shell or model command. Do not add scopes or copy host auth into model/check children. Host-only source fetch/PR publication uses existing authentication. Every role still snapshots and compares ALL refs in its own Git directory; a role mutating any unexpected ref fails. Independence is achieved by separate refs, never by filtering the guard. New parallel tasks must have disjoint components and distinct clone/git/common/object directories. Shared source-checkout operations remain serialized; the execution role never writes the original checkout. Public status exposes stable run/branch/isolation kind and sanitized reason, not private absolute paths.

Legacy linked worktrees keep their exact branch/path/run identity and existing same-repository action exclusion until their lifecycle is resolved. Do not migrate a live worktree into a clone or reset deadlines. Legacy versus new clone work may run together only if the legacy full-ref guard's shared git directory remains unaffected; source checkout mutations/preparation are serialized and unknown legacy owners fence repository preparation. This must be proven by tests; otherwise conservatively serialize that mixed repository until legacy work completes. Stable branch/run identity survives safe-ready owner handoff and process restart; never turn recovery into a new attempt without Issue16's durable stage/effect protocol.

### Initial and queued source resolution

Accepted `executor_profiles` admits only a fixed SHA or refs/heads|tags source_ref, not a remote-ref source mode. Candidate #16 `_source_current` resolves it in connection.checkout and requires equality to authenticated current main. An old local main/pinned SHA therefore prevents post-main refill; a dirty checkout is not a synchronization mechanism. Do not pretend those APIs already resolve accepted remote main.

For a queued run's first admission only, `resolve_group_source(config, task, snapshot, journal)` may use its exact private accepted_main_sources grant. Authenticate anchor→current M through the accepted-main proof contract below (same first-parent/100-step bounds/all task results/barrier and exact M CI); derive original S=B=M and persist an immutable source_resolution body with version1, run_id, mode (`accepted_main`), original profile ID/fingerprint/configured source_ref, anchor_sha, source_sha M, base_sha M and initial_main_proof_sha256. A pinned run records mode `pinned` and keeps legacy resolution. Source resolution is host authority, not a model-selected source or an edit to the old profile. Require all existing admission identity/dependency/criteria/private execution checks; only the explicitly granted source resolution differs.

Preparation then uses the safe owned standalone clone, fetches verified M into that clone through existing bounded Git containment and confirms clean checkout/head/source proof before any role. It may read/copy committed Git objects from the configured checkout with no-local/no-hardlinks, but never reads dirty working files as source, moves local main, fetches into the user's Git directory, writes user refs/files or substitutes another executable/repository. Original source metadata is written once only after host proof; a committed source/clone intent cannot be redirected or recreated. Freshly revalidate M/proof/grant before clone fetch, admission finalization and every continuation. If main changes during this preparation, park/fence as appropriate rather than rebinding original S or silently restarting. A ready queued task admitted after an earlier task completes resolves the new accepted M under the existing installed grant, without chat/local-main/config rewriting. Existing runs use the base-epoch mechanism; they never call this initial resolver to replace their S. No accepted_main_sources grant means visible `source_pinned_stale` when old source_ref differs, preserving legacy behavior.

## Repository integration and main changes

Development slots, groups and clones do not create independent merge queues. All groups in a repository share one integration barrier. #18 reads authenticated GitHub actual main/PR identities and existing genuine postmerge receipts. It does not add merge, close or fabricated approval operations. When #17 is accepted, its journal/worker remains owner of PR head/base verdicts and merge effects; #18 consumes observations, not a cross-SQLite transaction. Any lost or stale read leaves the barrier closed. At most one merge/main cycle may be active per repository.

A main change invalidates all waiting candidate head/base acceptance. Preserve old receipts as superseded and mark `base_changed`; no stage/PR approval or check evidence bound to the prior baseline may authorize a new effect. #18 must detect/report stale candidates even when #17 is unavailable, and must never claim them merge-ready. #17 integration is gated on its accepted actual contract; #18 can ship routing/development scheduling with `pr_worker_unavailable` status while making no automated merge claim.

### Immutable admission and additive trusted-base epochs

Never overwrite `run.source_sha` (original S), `run.base_sha` (original admission main B), admission body/digest, Issue/run/delivery/branch/workspace identity, criteria or scope policy to make a base import pass. Add host-owned `base_epoch` records, distinct from capacity epochs. Epoch0 preserves existing comparison authority: scope_base=S, diff_base=B; requests expose both and the original source-to-checkpoint delta. Group runs whose S differs from B retain that distinction and may proceed only under existing original authority; automatic base update is ineligible (`base_manual_required`). No preexisting approved feature delta or divergence is silently dropped or reclassified.

For automatic update require S==B, S and previous epoch scope_base P on the new main M's first-parent ancestry, and P equal the previous epoch diff_base. Non-ancestry, history rewrite, inaccessible history, more than 100 first-parent steps or any unsupported provenance yields visible manual needs_input without mutation. Epoch N>0 sets scope_base=diff_base=M only after the authenticated, disjoint, observed import below. The epoch contains exactly version1, run_id, epoch integer, previous_epoch_sha256, original_source_sha, original_admission_base_sha, admission_sha256, scope_base_sha, diff_base_sha, accepted_main_proof_sha256, pre_checkpoint_sha, pre_product_sha256, pre_task_delta_sha256, external_delta_sha256, post_checkpoint_sha, post_product_sha256, post_task_delta_sha256, update_id and authorization_sha256. Epoch0 uses null previous_epoch_sha256, external_delta_sha256 and update_id, and original source as initial checkpoints; its full source product manifest is frozen by the host. Its accepted_main_proof_sha256 is null only for pinned source resolution. In accepted_main mode it must equal the immutable source_resolution.initial_main_proof_sha256, with the identical binding in the journal, role requests/results, host checks and publication inputs. This initial proof does not create a base update or replace the source grant; its real provenance and freshness remain revalidated. Hash canonical JSON; immutable bodies and previous-digest chaining prevent replacement. A pending update is not an active epoch.

It must establish an accepted anchor for original S and every first-parent main step P..M: authentic merge-event identity, all task markers mapped to exact repository/Issue ID/task identities, every required task's independent exact-step postmerge receipt, successful required platforms and publisher-driven closed Issue, with no newer conflicting/reopened lifecycle. A direct/unattributed main step, unknown task marker, absent receipt/closure or unavailable check is `accepted_main_unproven`, not an exemption. A receipt for another main commit cannot attest this step. Validate exact M's current required-platform CI and the repository barrier's completed prior main/postmerge cycle with no pending or failed cycle. If #17 is absent, existing authenticated exact-main postmerge/closure evidence can prove a completed observed cycle; an unobservable pending integration leaves the barrier closed, never guessed open. This proof does not grant a merge operation.

Persist a host-built version1 proof containing repository, original accepted-anchor receipt digest, prior_base_sha P, main_sha M, required_platforms, exact CI run/check/bundle identities+digest, ordered accepted_steps and repository_barrier observation digest. Each accepted step binds main_sha, first-parent SHA, merge-event digest, independent postmerge receipt digest and all mapped task tuples (Issue/Issue ID/task ID, receipt digest, publisher publication identity, closed-observation digest). Host observations include provenance/time but timestamps/Boolean flags alone never authorize. Require actual main from authenticated API and the configured verified remote to agree on M. Revalidate this entire proof and private grant immediately before each fetch/merge phase, epoch commit and subsequent role/check/publication continuation; caching only within one bounded source refresh is allowed. Source freshness checks use current epoch scope_base while original S/B remain audit facts. New main drift, proof/CI/closure revocation or private-authority drift blocks; no injected true predicate, model result or editable JSON is an accepted-main source. Persisted proof is history, not indefinitely reusable fresh authority.

### Task-only scope, whole diff and overlap exclusion

At a cleaned pre-update checkpoint H, compute T as the complete raw Git tree delta P→H (no-renames, including mode/add/delete changes, host-projected artifacts separately attested) and E as P→M from authenticated Git objects. Verify T against unchanged task allowed_paths and host-card/evidence rules BEFORE excluding anything. Working/untracked/staged mutations must first pass those old-baseline checks; unauthorized task edits cannot be laundered by resembling future main. Treat a rename as delete+add. If path sets of T and E intersect at all, including same-content or conflict-free overlapping edits, park `base_overlap/manual_required` before merge. Keep H and all task content; do not resolve, discard or overwrite it. This conservative rule intentionally defers overlapping shared-file integration to an explicit reviewed manual action.

For disjoint T/E, the host-only merge must produce the exact union of their Git blob/mode changes. Post head R must preserve every T entry, import exactly E and change no other path. Assert raw delta M→R equals T, and compare full expected/result tree manifests, including protected cards/evidence against their respective host attestations. Hash both complete pre/post product manifests and raw deltas. A successful update therefore excludes ONLY the exact authenticated accepted-main delta by adopting M as scope baseline; it does not create a path exemption list. All later working-tree/checkpoint mutations are checked against M for task allowed_paths, protected host evidence/cards and complete ref guards. An edit to an imported out-of-scope path still fails. Product snapshots still hash the complete product (including accepted main content), with the existing explicit host artifact exclusions, never just last-merge files.

`pipeline_inputs` owns baseline-aware product/scope/checkpoint validation. It receives original S plus an independently journal-validated epoch binding; it must not reinterpret a caller-supplied source_sha as M. The complete product-file manifest/hash retains the existing version1 files representation and canonical file hashes; the separate versioned group input binds its epoch and task delta. The base-update post_checkpoint phase is a read-only host attestation of already observed merge commit R/tree/product/delta, not another commit or replacement head. Group stage manifests, role requests, host-check inputs and publication proofs bind epoch/digest, scope_base_sha, diff_base_sha, proof digest, full product digest and task_delta digest. Every post-update executor/reviewer sees complete original admission/epoch chain and full M→current checkpoint task diff, alongside full product/spec/plan/criteria, not merely H→R or the latest commit. Development reviewer reviews ALL task delta at M; final PR acceptance reviews the whole actual PR diff against freshly verified exact main/head, which must match the current epoch or become stale. Original S→H history remains visible for audit, not a substitute scope baseline after an accepted epoch.

### Safe boundary, phases and invalidation

If drift is noticed during a role/check, stop scheduling downstream work and request bounded cancellation through existing containment. Never merge/fetch into files/refs used by a live role/reviewer. Positive process-tree cleanup, full-ref/expected-head verification and no unresolved effects are required. Preserve authorized dirty output by a host-only pre-update checkpoint using OLD epoch scope/host-artifact validation and completed-or-failed attempt cleanup proof; it is not stage acceptance. This narrow host checkpoint may tolerate only known source-main drift, never revoked private authority, changed task criteria, scope/ref mutation or unknown cleanup. If it cannot safely freeze, park with content preserved. No role may continue on a fabricated safe-ready state. Before the merge, H must be durably checkpointed, worktree/index clean and bound to expected branch/head; reviewer detached worktrees must be cleaned/proven inactive. Unknown owners retain all fencing.

The installation grant bounds attempts: at most max_updates base-update intents per task (default0, maximum2); each committed intent consumes one update count even if later parked/unknown. Existing deadlines, role/process/check counters and per-stage rework counts are preserved. New model/check launches still consume their original budgets.
