### Typed host resource observation and conservative arithmetic

group_resources.observe_host(policy, *, deadline) returns closed version1 host observation: observation_id UUID, installation_id, policy_epoch, boot_id, process_id, monotonic_ns, observed_at UTC, expires_monotonic_ns, platform, cpu_millis nullable, available_memory_bytes nullable, limitations list, harness_pools map, provenance map, status available|fallback|unavailable, reason. CPU is effective affinity/quota-constrained logical capacity; available memory is currently usable bytes constrained by a supported host/container limit. No CPU load average or credential quota is inferred. A sample is valid for at most 5 seconds, collected within a 2-second monotonic budget. Backward clock, reboot, foreign collector PID, unsupported constraining mechanism, missing provenance or stale sample => resource_unavailable. Samples are collected by the same claiming host process; durable copies are audit history, not restart authority. No external caller may insert a JSON sample and make it trusted.

Windows collector uses ctypes native GetActiveProcessorCount/GetProcessAffinityMask, GlobalMemoryStatusEx and IsProcessInJob/QueryInformationJobObject where applicable. If an enclosing job's CPU/memory constraints cannot be reliably resolved, that capability is unknown. Linux uses sched_getaffinity, /proc/meminfo MemAvailable and supported unified cgroup-v2 cpu.max/memory.max/memory.current through verified current membership; unsupported nested/v1 arrangements are explicitly unknown. macOS uses ctypes sysctl for CPU/memory and Mach host_statistics64 for free+inactive+purgeable pages, bounded read-only native calls; inability to establish relevant platform constraints is unknown. No optional package/install/service, shell interpolated input or universal container-detection claim. Platform tests distinguish supported observations from unknown capability. Fixed read-only probes are allowed only from this enumerated native set. Explicit fallback substitutes only missing CPU/memory values, labeled fallback with policy provenance; absent fallback blocks fresh resource claims visibly. When any fallback value is used its max_executors additionally caps all new claims for that sample; it never increases a known measurement or another installed cap. A fallback is an operator estimate, not proof of OS resources.

Default admission reserves one logical CPU (1000 millis) and 1 GiB memory of headroom; these are measurement safety margins, not task-count ceilings. For a candidate, estimate is the maximum cpu_millis/memory_bytes across its six approved role profile entries plus 64 MiB/100 CPU millis helper overhead. Host-only prepare/check/publish actions use that same conservative task envelope so no action-kind bypass exists. A role action charges its actual approved profile pool; host-only actions charge the primary development_executor pool, still using the full six-role maximum envelope. Record these estimates and pool mapping immutably per run; edits revoke authorization rather than reset budgets. Available CPU budget is max(0,observed_cpu-1000) and memory budget max(0,observed_available_memory-1GiB). Apply optional installed CPU/memory ceilings by minimum. Subtract ALL held resource envelopes from those budgets, including unknowns; this deliberately double-counts currently resident process memory against free memory and is conservative. Atomic feasibility is sum(held)+candidate <= available budget in both dimensions, plus all optional count/pool/group limits. It uses checked integer arithmetic; overflow refuses claims. Low-resource hosts may yield zero capacity. No minimum-one or hardcoded-two fallback. Measurement/admission estimates do not limit a child's actual resource use, reserve OS memory, or create an OS/credential sandbox; deadlines/containment remain actual process controls.

An installation explicitly assigns authorized tasks to project groups and roles, runs independent work within shared capacity, and refills available slots without an active chat. Waiting tasks expose routing, dependency, capacity and ownership reasons. ### Immutable admission and additive trusted-base epochs

### Task-only scope, whole diff and overlap exclusion

At a cleaned pre-update checkpoint H, compute T as the complete raw Git tree delta P→H (no-renames, including mode/add/delete changes, host-projected artifacts separately attested) and E as P→M from authenticated Git objects. Verify T against unchanged task allowed_paths and host-card/evidence rules BEFORE excluding anything. If path sets of T and E intersect at all, including same-content or conflict-free overlapping edits, park `base_overlap/manual_required` before merge. Keep H and all task content; do not resolve, discard or overwrite it. This conservative rule intentionally defers overlapping shared-file integration to an explicit reviewed manual action.

For disjoint T/E, the host-only merge must produce the exact union of their Git blob/mode changes. Post head R must preserve every T entry, import exactly E and change no other path. Assert raw delta M→R equals T, and compare full expected/result tree manifests, including protected cards/evidence against their respective host attestations. Hash both complete pre/post product manifests and raw deltas. A successful update therefore excludes ONLY the exact authenticated accepted-main delta by adopting M as scope baseline; it does not create a path exemption list. All later working-tree/checkpoint mutations are checked against M for task allowed_paths, protected host evidence/cards and complete ref guards. An edit to an imported out-of-scope path still fails. Product snapshots still hash the complete product (including accepted main content), with the existing explicit host artifact exclusions, never just last-merge files.

`pipeline_inputs` owns baseline-aware product/scope/checkpoint validation. ### Registered G discovery, never delivery redirection

An explicit host invocation with `--groups-config G` may register the already validated G against its exact canonical pipeline J only after journal v2 migration, with a stopped controller and no conflicting live execution owner. Registration stores immutable installation UUID, canonical J physical path identity and canonical G path, and an append-only policy/capacity epoch. G and its bytes must pass existing group/pipeline/executor/connection validation; registration never originates from Issue/model text, delivery content or arbitrary JSON submitted to the journal.

For a registered J, group-aware current runtime commands may omit the G flag and discover **only that registered G path** from J. They must fresh-read/validate that same private G and compare its raw policy digest, authorization digest and capacity epoch before any new admission/claim/effect. This is registered group-mode discovery, not the omitted-G legacy execution path. A caller cannot select another G/J/installation, and a legacy direct claim cannot operate group-bound rows. The original adapter argv/cwd/backend fingerprint remains unchanged if it already names this SAME pipeline J.

Read-only status/reconcile-inspect and cancellation read typed journal metadata without reading G, installing tools or validating role pins. They may report binding/revocation/debt with fixed public reasons, but never emit the private G path. A missing/invalid/revoked G cannot disable inspection or a cancellation request. Execution/admission failure is visible and preserves old identities; a lookup may return the same valid existing v1 receipt or unknown under current revocation rules, never not_found for a known run and never a second submit.

Fresh **not-yet-admitted** tasks may use a separately explicit group-adapter backend configuration. Existing accepted/unknown dispatcher identities remain at their original backend/J and never receive a new delivery because of upgrade, migration or discovery. A legacy executor/dispatcher journal is not a pipeline v1 database and cannot enter this migration. The present Issue18 legacy delivery is retained exactly where it was admitted.

If the actual installed argv/cwd changes when a release is moved, discovery does not authorize that change. Retain the original adapter identity where the installation can safely update its runtime without changing argv, or leave that backend conservatively fenced. Old v1 binaries must refuse v2 J. Never edit committed backend fingerprints or copy/reset a journal to make a new path appear eligible.

### Policy revision and capacity epoch rules

Registered G/J/path/installation identity is immutable. A host restart with explicit G may validate and append a new policy/capacity epoch at the same binding. Capacity-only edits preserve authorization_sha256; other authorization edits create a new authority digest. Existing runs retain their original binding/digest/deadline/counters. Changed authority parks/fences old runs according to the accepted spec; this operation does not reauthorize or unpark them. New tasks may use the newly explicitly registered validated policy only through the original executor/pipeline allowlists. There is no old-run reauthorization command in this release.

Each epoch stores nullable explicit group/global/pipeline/executor caps, their minimum when any exist, resource policy, together with raw G digest, authority digest and the normalized per-project/group capacity matrix. A missing old group never hides its existing reservations. Reductions below held reservations record debt and reject new reservations without killing owners. Awaiting PR/main tasks retain product/component reservation but release execution lease after positive cleanup; clean ready_for_pr with disabled publication and clean needs_input may release execution capacity but retain product/component ownership. Unknowns retain both. Existing legacy rows are conservatively represented and counted at G adoption.

Every claim path in a registered J, including `claim(...max_active=2)` with no G argument, must consult that persisted epoch AND fresh host sample, never a caller maximum alone. Before creating a new reservation it verifies that the registered G bytes still match the current committed policy digest, without treating the bytes as proof of role/dependency readiness. If G has changed or vanished, no new reservation is made until fresh host validation/epoch registration; already reserved actions still require their normal fresh execution authority. A capacity-only reload is an explicit validated epoch transition, not an in-memory overwrite. Status/cancel/inspect remain independent of this check.

## 4. Proposed explicit migration algorithm
