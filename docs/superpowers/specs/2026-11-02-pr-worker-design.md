## Intent and scope

Run a durable local watch process which takes only explicitly authorized PRs, launches a fresh independent whole-diff reviewer, publishes `task-tower/pr-acceptance`, merges once under the project's existing rules, and holds the repository barrier until exact-main CI, independent postmerge acceptance and verified automatic Issue closure succeed. No agent in the active chat performs those transitions in the real pilot.

Python 3.11+ standard library only; Windows, macOS and Linux. Reuse existing installed Codex/custom executables, private connections, pinned Superpowers instructions and process containment. No installation, model selection, new credential scopes, protection edits, force pushes, manual Issue closure, rollback or background-service installation. A started watch is persistent independently of a model chat; it is not automatically restarted after machine/process death. #18 owns general groups, #19 distributed ownership, #25 supervision and #26 broader recovery. This feature has one local writer per repository, not an unattended distributed pool.

Issue #16 owns accepted stages and PR creation. This worker neither accepts development stages nor rewrites its pipeline journal. Task3 binds to accepted main `7586df4ac2e59316521463b7526089c8314024e4`, including integrated16 publication/history contracts and63 fetch timeout correction. Integrate this accepted foundation before imports/implementation; reconcile tests and obtain fresh branch acceptance after main advances. The six source schemas remain unchanged. ## Durable ownership, merge and barrier

Private SQLite PR journal owns PR intake/review/publication/merge, distinct from dispatcher/executor/pipeline/postmerge databases. One persistent repository barrier row, one owner UUID and OS advisory lock held by the watch process; duplicate local watcher fails before effects. Restart can read old state but cannot steal a running/unknown owner or retry an intent merely because time elapsed. Bounded read-only reconciliation consumes uniquely matching positive observations; owner-loss or ambiguous effects remain fenced for explicit recovery outside this milestone. No journal deletion/reset/retry-unknown command.

PR state sequence: discovered -> validating -> reviewing -> reviewed -> publishing_acceptance -> accepted -> merge_intent -> merge_pending -> awaiting_main -> awaiting_postmerge -> awaiting_closure -> completed. Side states: stale, rejected, needs_input, unknown, cancelled, timed_out. Every transition CASes owner, binding/input hash and previous state. Repository barrier is acquired before merge intent and remains held across restart/unknown/cancellation until independently verified exact main/postmerge/automatic closure; cancellation after merge does not release it. Premerge rejection does not acquire barrier. A second PR may be reviewed but cannot merge while prior barrier is held; base change invalidates its prior receipt. Different repositories can progress independently; this is not distributed ownership.

Use `PUT /repos/{repository}/pulls/{number}/merge-async`, API version 2026-03-10, exactly `{sha:head, merge_method:merge, merge_action:direct_merge, bypass_rules:false}`. No synchronous fallback, default queue action, queue admission, rebase/squash or stacked/downstack scope. Persist full intended binding before the sole request. A 202 response records validated UUID and enters merge_pending; poll only its GET result. Pending keeps barrier; failed parks; enqueued is unsupported and never completion; 409/expired 404/lost response/unknown UUID is unknown, never a second PUT. A 200 merged response requires the same positive verification as a completed async result. Store the UUID/result observation durably within its documented 24-hour retention; expiry does not prove no merge.

Positive merge confirmation requires live PR merged=true, exact repository/target/head, observed merge commit, authoritative main equal to that commit, and merge object parents exactly `[accepted_base, accepted_head]` (method=merge). Unexpected actor/base/parents or any intervening main change fences the repository. Poll authoritative GitHubSource for the exact commit's real Actions event/artifacts and required platform success. Merely seeing a merge commit or green PR CI is insufficient. Latest relevant failed/retried/incomplete main CI blocks. The worker drives the trusted postmerge bridge automatically, then requires durable independent postmerge approval, successful publisher receipt and a fresh genuine `project_worker.verified_done` for the same Issue identity/commit plus live completed closure. A closed Issue alone never releases the barrier. Record exact main and receipt/publication hashes, then release atomically and allow next merge.
