# Архитектура агентной разработки

Дата: 2026-11-01
Редакция: 3 — GitHub как источник задач, независимые проекты и приватные подключения установки.
Статус: согласованная целевая архитектура с частично реализованными основаниями: overlay Codex, readiness CLI, интерактивный bootstrap, приватные подключения/книги и postmerge-приёмка. Project-first onboarding #24 и диспетчер #14 прошли приёмку main и автоматически закрыты. #15 и #22 выполняются параллельно в отдельных рабочих копиях; их слияния и приёмка main последовательны. Автономное исполнение разработки, фоновая приёмка PR/слияния, группы и ночной режим остаются планом; ручная оркестрация текущего чата не доказывает их работу. Актуальная последовательность и границы: [roadmap](../../roadmap.md), установка: [GitHub setup](../../github-setup.md).

## Назначение

Общая система для будущих проектов владельца: идеи из разных сессий попадают в единый пул, задачи автоматически выдаются командам агентов, проходят независимую приёмку и сохраняются в истории вместе с результатами. Для выбранных задач система работает автономно, в том числе ночью на включённом компьютере.

Superpowers — обязательная основа процесса каждого подключённого проекта. Башня и книги показывают состояние работы; готовый таск-менеджер хранит задачи; отдельный сервис организует исполнение.

## Согласованные принципы

- Три книги: идеи, задачи и «Библиотека проекта» для артефактов. До трёх записей на странице; окончательный масштаб определяется при проработке интерфейса. Запись открывает подробности, поддерживаются сортировка и фильтры.
- Книги являются контейнерами сущностей проекта: «Идеи» — предложения; «Задачи» — этапы реализации (GitHub Milestones), крупные фичи (родительские Issues) и их подзадачи; «Библиотека проекта» — связанные Markdown-артефакты. Иерархия фич берётся из native sub-issues, этап — из milestone, доска — из Project. Фича может охватывать несколько этапов: эти связи сохраняются раздельно, без дублирования задач. Записи без этапа остаются видимыми; недоступные связи помечаются явно. Текущий плоский CLI/HTML ещё не реализует эту целевую иерархию; требования относятся к #22/#23.
- Идеи не запускаются автоматически. Агент замечает идеи в обсуждении и предлагает сохранить их. Явная команда сохранить не требует повторного вопроса.
- Команда выполнить означает сохранить задачу и приступить к работе. При занятости или зависимостях задача ожидает в очереди.
- Переписка остаётся в исходной сессии. Карточка содержит ссылку на неё и самостоятельное описание задания.
- Задачи, сессии и агенты имеют разные идентификаторы и жизненные циклы. Смена сессии или исполнителя не теряет задачу.
- Выполненные задачи не удаляются: книга хранит описание результата, даты, ссылки на документы, коммиты и PR.
- Код и результаты исследований, дизайна и обсуждений закрепляются в репозитории. Для текстовых результатов используются Markdown-файлы в docs/ или спеках.
- Попадание результата в main обязательно для завершения. После слияния требуется успешная финальная приёмка.
- Для задач в режиме «Автономно» владелец разрешил слияние в main после успешной приёмки перед слиянием.

## Компоненты и ответственность

### Хранилище задач

Выбран GitHub: каждый проект владеет своим репозиторием, Issues и GitHub Project. Issues и история workflow являются источником задач и состояний, Project отображает их, Markdown-файлы репозитория хранят спеки, исследования и результаты. Три книги агрегируют подключённые источники, сохраняя идентификатор `owner/repository#issue`. Список подключений принадлежит установке и хранится вне исходников Task Tower; для нескольких машин допустим отдельный приватный репозиторий конфигурации. Репозиторий Task Tower содержит задачи разработки самого инструмента, а не задачи всех пользователей.

Распределённая очередь использует GitHub Actions и self-hosted runners проектов. Постоянное намерение запуска хранится в GitHub отдельно от ограниченной очереди Actions; один Issue исполняется последовательно, независимые Issues и проекты могут работать параллельно. История приёмки и артефакты привязаны к конкретной попытке workflow. Подробный контракт и границы текущего этапа: [спека подключений и книг](2026-11-01-github-projects-design.md). Текущая реализация поддерживает распределённую postmerge-приёмку; автоматическая разработка и барьер автоматических слияний остаются следующими этапами.

Данные исполнения, которых нет в выбранном продукте (запуски, захваты задач, события приёмки), могут храниться в отдельном журнале оркестратора со ссылкой по постоянному ID задачи. Один владелец каждого поля и правила обновления определяются адаптером; две независимые редактируемые копии статуса недопустимы.

### Сервис очередей и исполнения

Обычный постоянно работающий сервис, а не один агент-модель. Выбирает готовые задачи, закрепляет их за исполнением, запускает агентов, принимает события, учитывает зависимости, лимиты и остановки. Не требует ответа общего агента для каждого перехода.

Захват задачи атомарный: одновременно у неё один активный владелец исполнения. Повторная доставка события или запроса не создаёт вторую задачу, запуск или слияние. После перезапуска сервис сверяет незавершённые запуски; истечение срока захвата само по себе не разрешает дублирующее выполнение без проверки старого запуска.

Цикл агента, протокол инструментов и сохранение сессий переиспользуются из поддерживаемого runtime, например Codex или OpenHands. Собственный слой отвечает за очередь, переходы, права и адаптеры. Выбор runtime и проверка его работы на Windows входят в пилот; сохранение сессии не заменяет сверку фактического состояния репозитория и внешних операций.

### Агенты таск-менеджера

Помогают разбирать идеи, уточнять задания, предлагать группы и приоритеты, выявлять зависимости и разбирать нестандартные блокировки. Они не заменяют механический диспетчер и не управляют деталями реализации проекта. Изменения задания и решения сохраняются в карточке или репозитории.

### Команды проектов и групп

У проекта может быть несколько групп со своими очередями и агентами. Для Dialoid состав групп пока не определён; интерфейс, ядро и интеграции были примерами, а не утверждённой структурой.

Ведущий группы принимает цель, изучает правила и документы проекта, организует исполнителей и приёмщиков, возвращает результаты этапов. Группа может содержать ведущего, исполнителей и независимых приёмщиков; это роли, а не требование постоянно держать все процессы активными.

Группа задаёт область ответственности, маршрутизацию, навыки и права. Роли запускаются по потребности задачи. Постоянный штат процессов не является целью. Дополнительные ведущие и исполнители вводятся при измеримой пользе на независимой работе; обязательная приёмка этапов сохраняется, её объём соразмерен сложности задачи.

Задачи нескольких групп связываются общей родительской задачей. Зависимые подзадачи ждут принятого результата, независимые могут работать параллельно. Родительская задача закрывается после приёмки всех обязательных результатов и общей интеграции.

Предлагаемый стартовый лимит: одна активная задача на группу, несколько групп и проектов могут работать параллельно в пределах общего лимита. В одном репозитории слияния сериализуются, а изменения разрабатываются в изолированных рабочих копиях. Это проектное предложение, требующее подтверждения при утверждении спеки.

Очередь слияний удерживает следующий merge до успешной postmerge-приёмки предыдущего коммита. Разработка других задач может продолжаться, но их слияние ждёт этого барьера. При провале очередь остаётся остановленной до восстановления и успешной проверки main.

## Superpowers в каждом проекте

Подключение проекта включает инструкции, указывающие Superpowers как обязательный процесс, описание репозитория, команд проверок, групп и правил автономности. Конкретная установленная версия и применимые навыки фиксируются конфигурацией проекта; обновление процесса не должно молча менять уже выполняемую задачу.

Применимые навыки определяют проработку, спецификацию, планирование, исполнение, тестирование, ревью и проверку перед завершением. Оркестратор хранит свидетельства прохождения этапов и не подменяет их простым изменением статуса.

Superpowers задаёт методологию, но не обеспечивает надёжное исполнение и не доказывает качество продукта сам по себе. Сервис проверяет машинные условия переходов: принятую версию спеки, план, решения приёмщиков и актуальные свидетельства. Соблюдение процесса и выполнение исходной цели проверяются отдельно. Небольшая задача может иметь компактную спеку и короткие проверки без пропуска обязательных этапов.

Назначение агента-приёмщика не означает автоматического права обходить требование участия владельца из применимого навыка. Матрицу делегируемых согласований нужно явно утвердить и отразить в инструкциях проектов. Пока согласование не делегировано, выполнение останавливается с точным вопросом владельцу. Уже разрешённое автономное слияние повторного согласия не требует.

## Поток от сессии до результата

1. Общий инструмент захвата доступен агентам подключённых сессий. Он сохраняет идею или задачу с проектом, исходной формулировкой и ссылкой на сессию. Пул не получает автоматический доступ ко всем чатам: сессия должна иметь инструмент и инструкции по его использованию.
2. Идея попадает в книгу идей. Перевод в задачу сохраняет связь с исходной идеей.
3. Явное поручение создаёт задачу с намерением начать выполнение. Если требуется уточнение, задача сохраняется, получает блокировку и конкретный вопрос вместо выдуманных требований.
4. Сервис определяет группу по правилам маршрутизации. Неопределённое назначение разбирает агент-координатор; остальные очереди продолжают работу.
5. Готовая задача без невыполненных зависимостей захватывается сервисом и передаётся ведущему группы вместе с полным заданием и ссылками на контекст.
6. Исполнители и приёмщики проходят этапы. Сервис записывает события и обновляет книгу. Завершение ответа агента не означает завершение задачи.
7. Принятые изменения поступают в очередь слияний проекта. Если main изменился после проверок, кандидат актуализируется, а затронутые проверки повторяются до слияния.
8. После слияния проверяется итоговый main с фиксацией точного коммита. Только успешная приёмка этого результата переводит задачу в «Готово».
9. Сервис освобождает слот и берёт следующую независимую готовую задачу.

### События слияния из GitHub

Слияние PR получает отдельный event contract: repository, PR, точный merge SHA, связь с задачей, ID доставки и результаты проверок. GitHub-side hook запускает postmerge-проверки и публикует событие; локальный sync/очередь затем применяет его идемпотентно. Факт merge переводит задачу на postmerge, но не закрывает её. CI одной платформы не заменяет все обязательные проверки и независимого приёмщика. Недоставленные события восстанавливаются сверкой main. Первый экспортёр и его границы описаны в [спеке hook](2026-11-01-merge-event-design.md); автоматическое локальное получение ещё требуется реализовать.

## Этапы и независимая приёмка

| Этап | Результат | Приёмка |
| --- | --- | --- |
| Спецификация | MD-спека с требованиями и критериями | Полнота, границы, проверяемость и соблюдение процесса |
| Планирование | План реализации по Superpowers | Соответствие принятой спеке; включается в контроль готовности разработки |
| Разработка | Изменения и ссылки на коммиты | Независимое ревью реализации по спеке и правилам проекта |
| Тестирование до слияния | Отчёт с командами, результатами и версией кода | Проверка покрытия критериев и достоверности результатов |
| Приёмка PR | Решение по полному diff и точным head/base SHA | Отдельный от исполнителя приёмщик проверяет результат, тесты, CI и блокирующие замечания |
| Слияние | Принятый результат в main | Все обязательные предыдущие приёмки актуальны |
| Проверка после слияния | Проверки итогового main и отчёт | Независимое решение о завершении задачи |

Исполнитель не принимает собственный результат. Приёмщик использует исходное задание, принятую спеку и проверяемые артефакты, а не только пересказ исполнителя. Отчёт содержит решение, основания, замечания, ID роли/запуска и точную версию проверенного результата. Изменение результата делает затронутую приёмку неактуальной.

### Допуск PR к автономному слиянию

Разрешение владельца на автономную интеграцию хранится в приватной политике конкретного проекта. Для обычных согласованных задач Task Tower отдельный апрув в чате не требуется после прохождения всех ворот. Разрушительные операции, необратимые миграции, изменение области доступа/учётных данных и явные пользовательские решения требуют отдельного согласования. Разрешение одного проекта не переносится на другие репозитории автоматически.

Перед слиянием отдельный приёмщик PR изучает весь фактический diff, исходную задачу и принятую спеку, актуальность прежних приёмок, тестовые результаты и CI. Его решение `approve`, `reject` или `needs_input` содержит repository, PR number, точные head/base SHA, ID приёмщика, основания и блокирующие замечания. Зелёный CI без положительной приёмки PR не разрешает слияние. Любое изменение head или base делает это решение неактуальным.

В GitHub результат виден как отдельная проверка `task-tower/pr-acceptance`: `pending` до решения, `failure` при отказе, `success` только после принятия этого SHA. Отчёт публикуется как привязанный к коммиту review. Это агентная приёмка, а не подмена человеческого GitHub approval; защита репозитория не обходится. Оркестратор перед merge повторно сверяет head/base, проверки и отсутствие блокирующих замечаний и передаёт expected head SHA. В текущем пилоте этот допуск исполняет агент-оркестратор; серверное обязательное правило защиты ветки и отдельный фоновый сервис автослияния этим описанием не считаются установленными.

После merge требуется отдельная независимая postmerge-приёмка точного коммита в main. Следующее автоматическое слияние этого репозитория ждёт её успешного результата; завершение задачи и закрытие Issue подтверждаются отдельно. Артефакт приёмки PR публикуется вне изменяемого содержимого PR, чтобы запись решения сама не создавала новый head SHA.

Новая сессия приёмщика не гарантирует независимость ошибок моделей. Приёмщик изучает исходную цель и изменения, воспроизводит ключевую проверку и ищет контрпримеры. Приёмка включает пакет доказательств: commit SHA, версию среды, команды и коды завершения, ссылки на CI и тестовые отчёты; для UI — релевантный пользовательский сценарий и визуальные артефакты. Критерии результата задаются до реализации и связываются с проверками. Согласие нескольких агентов без этих доказательств не разрешает переход.

Обязательные проверки и правила допуска защищены от незаметного ослабления исполнителем. Изменения CI, тестов, инструкций и политики слияния требуют явного обоснования и отдельной приёмки по полномочиям проекта. Качество приёмщиков проверяется на известных дефектах и корректных изменениях: учитываются пропуски и ложные отказы.

Замечания возвращают задачу на нужный этап. Неуспешная проверка после слияния оставляет задачу незавершённой и блокирует дальнейшие слияния проекта до разбора; другие проекты могут продолжать работу. Политика исправления или отката требует отдельного согласования, автоматический откат этой спекой не разрешается.

Для задач без кода этап разработки означает создание MD-артефакта, тестирование — проверку источников, ссылок, критериев и применимых проверок документации; после слияния проверяется наличие и корректность результата в main. Неприменимые проверки помечаются с обоснованием.

Для пользовательских функций проверяется наблюдаемое поведение по исходной цели. Попадание в main и postmerge-приёмка остаются обязательным минимумом завершения. Развёртывание и проверка production — отдельные состояния; необходимость выпуска определяется задачей, универсальное требование деплоя не вводится.

## Контракт готовности проекта и полномочия

До автономного запуска проект получает версионируемое описание среды: ОС/образ, runtime, lockfiles, установку, запуск, команды проверок, тестовые сервисы и данные, доступные ресурсы и разрешённую сеть. Чистая рабочая копия должна воспроизводимо проходить подготовку и базовую проверку. Исходные поломки фиксируются отдельно от регрессий задачи; отсутствие достоверной исходной проверки блокирует ночной допуск.

Worktree изолирует изменения Git, но не процессы, порты, БД, сеть и секреты. Для параллельной работы отдельно обеспечиваются sandbox, пространства тестовых сервисов и жизненный цикл среды: создание, проверка готовности, очистка и восстановление.

Разделяются три решения: качество результата, разрешение действия и технический доступ. Исполнитель получает права рабочей ветки и необходимые инструменты; отдельный контроллер слияния изменяет main только при актуальных свидетельствах. Доступ к секретам, сети и внешним системам ограничен задачей и ролью. Разрешение автономного слияния не означает доступ к production, необратимым миграциям или автоматическому откату.

## Восстановление и управление сбоями

Сервис различает активность агента, живой процесс, ожидание провайдера, зависший инструмент, запрос разрешения и неизвестный исход внешней записи. Heartbeat подтверждает доступность процесса, но не прогресс задачи.

Временные транспортные ошибки получают ограниченные повторы; провал проверки возвращается исполнителю; ошибки авторизации и лимитов останавливают затронутое выполнение. После неизвестного исхода push или merge сначала сверяется репозиторий и удалённое состояние, затем принимается решение о продолжении. Слепой повтор внешнего действия запрещён.

Отмена и таймаут останавливают дочерние процессы, освобождают захват после сверки и выполняют уборку среды. Границы ответственности журнала runtime и журнала оркестратора определяются адаптером, включая восстановление после перезапуска и недоступности хранилища.

До ночного automerge проект получает процедуру восстановления main: условия остановки очереди, разрешённые исправления, полномочия на откат, повторные проверки и уведомление владельца. Пока политика не утверждена, действует остановка с сохранением причины; автоматический откат не разрешён.

## Статусы

Идеи: «Сохранена», «Переведена в задачу», «Архив».

Задачи: «Входящие», «Готова к работе», «В работе», «На приёмке», «Ожидает слияния», «Проверка после слияния», «Нужен ответ», «Заблокирована», «Готово», «Отменена».

Текущий этап хранится отдельно от общего статуса. Активность агента (работает, ждёт, ошибка, нет свежих данных) также отдельна: молчащий агент не считается ни успешным, ни завершившим задачу. У блокировки есть причина и условие продолжения.

## Минимальные данные и взаимодействие

Карточка: постоянный ID, название, описание, проект, группа, тип результата, теги, приоритет, даты создания/изменения/завершения, необязательный срок, источник-сессия, связи идей и задач, зависимости, критерии готовности, режим автономности, статус и этап, блокировки, ссылки на спеку, план, отчёты, PR и коммиты.

Запуск: ID задачи и попытки, роль агента, сессия исполнения, версия входного задания и среды, рабочая копия/ветка, проверяемый коммит, время начала/обновления/окончания, исход и причина остановки, расход моделей и проверок. Журнал связывает вызовы инструментов, отчёты, приёмки и внешние действия с конкретным запуском.

Передача работы: карточка и версия задания → подтверждение получения → события этапов → отчёт и артефакты → решение приёмщика. События имеют уникальный ID и сохраняются в журнале. Прямое общение агентов допустимо для уточнений, но решения, влияющие на выполнение, обязательно записываются в общий контекст задачи.

## Ночной режим

Режим выбирается для конкретной задачи. «Автономно» разрешает весь согласованный цикл, включая слияние после приёмки; режим «С участием владельца» останавливается в заданных точках.

Перед запуском задаются лимиты параллельности, времени, расходов/использования и повторных возвратов. Бюджет включает исполнителей, приёмщиков, повторные попытки и CI. Конкретные значения ещё не выбраны. При исчерпании лимита сервис прекращает новые запуски и останавливает активные циклы соответствующей области с сохранением результата и причины. Если провайдер не позволяет жёстко ограничить стоимость, это фиксируется до допуска; гарантированный денежный предел не обещается. Вопросы разрешений, недоступные зависимости и неоднозначности не трактуются как разрешение действовать.

Автономность учитывает класс риска задачи и готовность проекта. Точные классы и чувствительные действия определяются проектной политикой до пилота; общий флаг не расширяет права сверх неё. Уже данное владельцем разрешение автономного слияния сохраняется при выполнении согласованных условий.

Для локального исполнения компьютер должен оставаться включённым, исполнитель — работающим, репозитории — доступными. Выключение и сон прерывают локальную работу. Непрерывная работа при выключенном ПК потребует отдельно выбранного удалённого исполнения.

Предпочтительный первый путь интеграции для исследования — официальный codex exec или SDK; app-server рассматривается при необходимости постоянных разговоров и управления разрешениями. Не предполагается, что эти интерфейсы автоматически управляют уже открытыми чатами приложения.

## Башня и книги

Башня — проект, этаж — сессия, персонажи — агенты. Три книги дают отдельные представления идей, задач и артефактов проекта. До трёх записей на странице показывают название, статус, теги и дату; подробности задачи раскрывают этап, исполнение, приёмку, блокировки и результаты. Фильтры включают проект, группу, статус и выполненные задачи.

Третья книга — «Библиотека проекта»: спеки, исследования, дизайн, принятые решения и отчёты. Это каталог результатов со ссылками на Markdown-файлы в docs/ или спеках репозитория, а не отдельная копия их содержимого. Запись связывает артефакт с задачей, типом документа, датой, тегами и версией/коммитом. Из задачи можно перейти к результату в библиотеке, из результата — к породившей его задаче. Документ доступен и до завершения задачи; библиотека различает рабочую версию и результат, закреплённый в main. Источником истины для содержимого остаётся файл в репозитории.

Каталог различает черновик, принятый и заменённый документ, хранит связь с заменяющей версией. Ссылка на текущий файл служит чтению актуального текста; отдельная ссылка на коммит фиксирует версию, использованную при выполнении и приёмке. Инструкции и навыки проекта обновляются проверяемыми изменениями репозитория; постоянная память агента не является единственным источником решений.

Текущий сборщик башни читает внутренние данные Codex только для наблюдения. Он не становится механизмом выдачи задач и не записывает в внутреннюю БД Codex. Для управления используются отдельные поддерживаемые интерфейсы. При недоступности источника книга явно показывает несвежесть данных и не имитирует успешные переходы.

## Критерии принятия архитектуры при реализации

- Задача из любой подключённой сессии появляется в едином пуле один раз, со ссылкой на источник.
- Идея не исполняется без перевода в задачу; явное поручение запускается при готовности и свободном слоте.
- Две группы могут выполнять независимые задачи параллельно; одна задача не получает двух активных исполнений.
- Нельзя пройти обязательный этап без актуальной независимой приёмки.
- Завершение ответа, успешные тесты до слияния или одно слияние по отдельности не закрывают задачу.
- «Готово» содержит результат в main и успешную приёмку после слияния с указанием коммита.
- После остановки и перезапуска система восстанавливает достоверное состояние без дублирующего запуска.
- Выполненные задачи и MD-результаты остаются доступны из книги.
- Исполнитель не может незаметно ослабить обязательные проверки или выдать себе право слияния.
- Допуск к ночной работе требует воспроизводимой среды, проверенных приёмщиков, действующих лимитов и процедуры восстановления main.

## Пилот Dialoid и измерение пользы

Порядок внедрения: аудит готовности Dialoid → одна небольшая задача через готовый runtime и весь цикл → небольшой набор задач разных типов → проверка сбоев и измерение → тонкая очередь и интерфейс книг → параллельные группы и подключение новых проектов. Глубокий рескин, постоянный штат агентов и тяжёлый workflow engine откладываются до подтверждённой необходимости.

На наборе задач (баг, функция, UI, документация, интеграция — по применимости проекта) сравниваются минимальный состав исполнителя и приёмки с расширенной командой. В обоих вариантах сохраняются Superpowers и обязательные этапы. Один успешный проход не доказывает надёжность ночной работы.

Метрики: доля принятых задач без вмешательства, время владельца, время до готовности, стоимость принятого результата, число возвратов, пропущенные дефекты и ложные отказы, регрессии после слияния, откаты и причины ночных остановок. Число агентов, коммитов и занятых часов не считается самостоятельной мерой успеха. Пороги качества и стоимости задаются до пилота.

Допуск к ночному automerge проверяется испытаниями:

- Обязательные проверки и приёмки относятся к точному принятому коммиту; контрольные дефекты не получают допуск.
- Убийство процесса до/после push, перезапуск и потеря связи после merge не создают повторного исполнения или слияния.
- Зависший тест, исчерпание лимита и отмена останавливают активный цикл и дочерние процессы.
- Недоступность хранилища, заполнение диска и сбой тестового сервиса дают объяснимую остановку и восстанавливаемое состояние.
- Поломка main останавливает слияния и обрабатывается по утверждённой процедуре восстановления.

Провал обязательного испытания блокирует ночной automerge до исправления и повторной проверки. Прохождение малого набора не заменяет дальнейший мониторинг и выборочную проверку владельцем.

## Открытые решения перед реализацией

1. Совместный выбор исполнителя, хранилища и размещения по пилоту; проверка API, доступности функций аккаунта и расходов.
2. Какие согласования Superpowers делегированы приёмщикам для автономных задач.
3. Состав групп Dialoid и правила передачи общих задач между группами.
4. Тип памяти ведущих: постоянные сессии или восстановление из документов. В обоих случаях документы и карточки обязательны.
5. Утверждение стартового лимита одной задачи на группу, ночных бюджетов и числа повторов.
6. Политика исправления main после провала финальной приёмки.
7. Конкретная среда Dialoid, sandbox, тестовые данные, исходные проверки и права ролей, включая чувствительные файлы и действия.
8. Классы риска, набор пилотных задач и контрольных дефектов, пороги качества, стоимости и вмешательства владельца.

Выбор языка сервиса, формата внутренних событий, схемы адаптеров и точного макета страниц оставляется реализации после согласования требований. Первый пилот — одна задача Dialoid через полный цикл; расширение на несколько групп и проектов следует после проверки пилота.
