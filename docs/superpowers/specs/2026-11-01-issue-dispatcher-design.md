# Issue dispatcher design — TT-DISPATCH-001 (#14)

## Intent and boundary

After #24's exact-main postmerge acceptance and automatic closure, select explicitly authorized ready GitHub tasks and deliver their identities to a trusted installation adapter. This is the next authorized backlog stage. This document does not implement the development executor (#15), independent development pipeline (#16), automated PR intake/merge (#17), distributed scheduling, or night readiness. The current chat's continuous authorized work is distinct from a shipped background service.

Python 3.11+ standard library only. Existing connections, GitHubTasks metadata parser, GitHubSource and project_worker.verified_done remain authoritative interfaces. GitHub Issue prose is untrusted data. No Issue field supplies executable paths, arguments, environment, shell fragments, working directories, or adapter configuration. Dispatcher never changes GitHub Issues, comments, Projects or labels.

## Installation authority

Use existing private connections plus a separate private dispatcher JSON config outside all connected checkouts. Version 1 config has `version`, `allowlist` (default empty), optional `backend`, and `interval_seconds` (default 60, integer 5..3600). Reject unknown keys and invalid types rather than guessing. An allowlist entry is exactly `{repository, issue, task_id}`; Issue is a positive integer (never bool), task ID matches `TT-[A-Z0-9-]+`, and repository must match a connected repository. Normalize repository identity with casefold; reject duplicate entries and conflicting task IDs. No enabled allowlist or no backend means disabled exit 0 with visible fixed reasons; skip GitHub and adapter calls so unrelated source outages cannot turn a disabled dispatcher into an operational failure.

Backend is private trusted configuration with a custom file adapter (parent design ruling, reusing ReviewRunner and existing process lifecycle): `{argv, cwd, timeout_seconds}`. argv is a nonempty list of nonempty trusted template strings supporting only `{request}`, `{result}` and `{checkout}` placeholders, cwd resolves to an existing absolute directory, timeout is an integer 1..300. Resolve executable once using trusted config/PATH, reject implicit `.cmd`/`.bat` shells, and run an argument array with shell=False. Do not interpolate Issue content. Credentials remain in the host authentication environment; never store config/argv/environment/raw process output in journal or reports. The adapter always represents the trusted custom harness; do not auto-select/install a model or invoke a development agent directly.

The installation journal location is an explicit CLI path outside connected checkouts, shared by all local dispatcher processes for that installation. Resolve canonical paths and reject links/junctions using existing safe-path conventions before creating files. Config, connections, journal and SQLite sidecar paths must be distinct, including case and existing hard-link aliases. Reject journal/config paths inside connected checkouts; recheck before writable opens. Never overwrite an input file as a journal. Losing/deleting/changing the journal forfeits local deduplication; document preservation as required. This is not distributed locking across machines or independent journal copies.

## Fresh source snapshot and ready selection

Fetch a bounded complete Issue list for each connected project every tick using GitHubTasks.list_issues. Track per-project unavailable sources with fixed, sanitized diagnostic codes. Do not reuse a previous tick's readiness or dependency proofs. A source failure prevents selection for that project and candidates depending on it; independent healthy projects continue. Malformed/unavailable sources (transport, pagination, listing schema, invalid/duplicate Issue identity) block the affected project and make its task-ID index unavailable. A valid Issue identity with malformed task metadata is an individual exclusion, cannot resolve dependency IDs, and does not block healthy unrelated tasks.

For each allowlisted identity require GitHub `state == open`, parsed metadata `kind == task`, `mode == autonomous`, `status == open`, and an exact expected task-ID match. Reconcile all present `task_id`, `legacy_id`, `id` aliases: each must equal the expected task ID; disagreement, missing identity, or duplicate task IDs in a repository excludes the candidate. Priority must be exactly P0/P1/P2/P3; missing priority defaults to P3 (builder ruling), invalid priority excludes the candidate. Effective lifecycle must remain open: use issue_lifecycle so an existing running/done/needs_input remote attempt cannot be redispatched from stale body metadata. A lifecycle read/parse error excludes that candidate. Ideas, closed Issues, blocked/non-open metadata, malformed values and explicit unresolved dependencies cannot run.

Sort ready candidates by numeric priority P0..P3, normalized repository, then numeric Issue number. Each tick permits at most 8 new submits and 8 unknown lookups. New submissions follow this deterministic order; existing journal rows consume no submit budget, so later tasks advance next tick. Unknown lookups use round-robin identity order with a durable journal cursor advanced before each invocation, preventing starvation across ticks/restarts. Separate budgets prevent unknown outcomes starving new work. Budget exhaustion reports deferred identities without operational failure. These are per-process per-tick bounds, not global execution capacity, aggregate installation rate limiting or active-run scheduling. Journal deduplication removes accepted/unknown deliveries from first submission. Snapshot/report lists ready, excluded, dependency-blocked, unavailable and delivery states using identity and fixed reason codes; no body, title, credentials or backend output.

## Dependencies and verified completion

Keep canonical Issue references separate from legacy task IDs. `blocked_by` is a list of canonical qualified strings `owner/repository#N` (positive decimal Issue number), matching existing backlog metadata; `blocked_by_task_ids` is a list of task-ID strings, resolved only within the candidate's repository. Reject duplicates, invalid entries, self-reference and unsupported/unconnected repositories. Missing fields mean empty lists. Do not interpret a bare task ID as an Issue reference or infer a repository from global search.

When both fields are supplied, their resolved repository/Issue sets must agree exactly. Resolve task IDs using the complete same-tick repository metadata index; missing or multiple matches blocks the candidate. A conflicting identity alias cannot resolve a dependency. Unknown, unavailable or malformed dependencies block that candidate with a visible reason. Cross-project dependency failures propagate only to their consumers.

For every resolved dependency, fetch its fresh Issue and call `verified_done(connection, store, source, issue)` during this tick, using that dependency repository's connection. Closed state, `status: done`, accepted body stages, board state and cached prior approval never suffice. Existing verified_done checks current lifecycle, trusted publication receipts, CI/bundle provenance and main ancestry. False or any retrieval/validation failure blocks the consumer. Same-tick proof caching per dependency identity is permitted; never cache across ticks. Cycles remain blocked naturally because no member has fresh verified completion; do not introduce a graph scheduler.

## Durable delivery and recovery

SQLite table `deliveries` has primary key `(repository, issue)`, expected task ID, stable random UUID delivery_id, backend fingerprint, status (`unknown` or `accepted`), sanitized detail code and optional bounded accepted receipt ID. Fingerprint is SHA-256 of canonical trusted backend argv/cwd/timeout JSON; never persist its input. Journal metadata additionally stores the durable round-robin lookup cursor without altering delivery identity/status. Schema/version mismatch, corruption, locking exhaustion, unsafe paths or failed durable writes fail closed: no submit without a committed intent. Use BEGIN IMMEDIATE and a unique insert so competing local workers cannot both win. A transaction failure must never be treated as a successful reservation.

Immediately before reserve/send, refetch Issue and lifecycle and rerun allowlist, task metadata and dependency checks with fresh per-send proofs. A failed revalidation prevents submit. GitHub offers no atomic read-and-send transaction; edits after the final check remain a documented best-effort race. First delivery inserts and commits `unknown` BEFORE starting the process. Only the caller that inserted this row may invoke submit, once. A crash between commit and launch deliberately leaves an unknown outcome. Existing rows never become eligible for submit again, even after timeout, not_found, config changes, changed task metadata, a reboot, or another worker. No expiring lease/reclaim, reset command, automatic retry or exactly-once claim.

An accepted acknowledgment atomically changes unknown to accepted, preserving identity, task ID, delivery ID and backend fingerprint. Accepted rows never invoke submit or lookup again. Unknown rows may invoke read-only lookup on subsequent ticks/restarts only when the original private allowlist authorization, current fresh source task identity and backend fingerprint match the journal. Readiness need not remain open for reconciliation, but unavailable/malformed source, revoked allowlist or unsafe config permits no adapter call. Config/identity mismatch remains needs_input and invokes neither operation. Lookup accepted records accepted; lookup not_found/unknown remains unknown and visibly needs_input. Operator investigation/reconciliation is outside #14; the dispatcher never deletes an intent to permit retry. Concurrent read-only lookups are harmless and cannot submit. A stale negative lookup cannot downgrade an accepted row.

## Adapter protocol and process boundary

Create a managed TemporaryDirectory and resolve its canonical path before passing it to the backend. Write request.json as UTF-8 JSON with exactly `{operation, delivery_id, repository, issue, task_id, runner_label}`; operation is `submit` or `lookup`. runner_label comes from the trusted project connection. Never send body/title or raw metadata. Format only the three trusted argv placeholders using managed request/result paths and configured cwd as checkout. Invoke existing `processes.run_command` unchanged: shell=False, stdin DEVNULL, existing timeout/process-tree cleanup, output hashes/counts only. Raw stdout/stderr are never protocol or report data. The adapter writes result.json; reject missing, linked/reparse, nonregular or greater-than-64-KiB results before a bounded read, and discard temporary files after validation. Never write secrets into request JSON. Do not modify processes.py or windows_job.py for #14.
Successful exit zero and a passed process lifecycle require result.json to contain one JSON object with exactly `version: 1`, matching `delivery_id`, `status` (`accepted`, `unknown`, or lookup-only `not_found`), and, for accepted, `receipt_id` (ASCII token matching `[A-Za-z0-9._:-]{1,256}`). Even valid output remains untrusted: never echo receipt text in diagnostics or treat it as a command, URL or instruction; only the private journal stores this bounded token. Reject extra fields, identity mismatch, duplicate JSON keys, trailing objects, invalid UTF-8, oversized result, bool version and malformed values. Nonzero exit, launch failure, timeout, failed cleanup or invalid protocol leaves unknown/needs_input. No raw output is persisted. A trusted lookup adapter contract MUST be read-only and must never create work. Local dispatcher cannot prove a custom backend obeys that trust contract.

## CLI and visibility

Expose `python -m task_tower dispatcher --connections PATH --config PATH --journal PATH` with mutually exclusive `--once` and `--status`, plus `--dry-run`. Default is the foreground bounded-interval polling loop; Ctrl-C exits cleanly, with no installer, service registration or hidden daemon. --once performs one tick. --status reads the journal using SQLite read-only mode without GitHub/backend calls or creating files; a missing journal yields empty status. Reject --status with --dry-run. --dry-run may fetch/read GitHub and compute a plan but must not create directories, open SQLite writable, mutate journal bytes, invoke adapter, or mutate GitHub; missing journal is read-only empty state. Existing private configuration files are never rewritten.

Emit sanitized JSON; project errors remain per-project and healthy work proceeds. Exit 0 for a completed tick/read-only report (including ordinary not-ready/disabled tasks), 1 for source/backend/journal operational failures or unresolved delivery outcomes, 2 for invalid CLI/config. Loop continues after per-project failures and sleeps interval between ticks; invalid global config or journal integrity failure stops it. A source failure is never a signal to mark another project's tasks complete.

## Acceptance and evidence

Tests use TemporaryDirectory paths resolved before configuring connections, Python helper adapters launched with sys.executable, fake GitHub transports and injected factories/clocks/sleep. Cover deterministic ordering, metadata attacks, both dependency forms, fresh verified_done proofs, partial source errors, private config defaults, malformed protocol, process timeout, crash boundary, two processes sharing one journal, restart lookup and byte-identical dry-run. Full CLI suite must pass on Python 3.11+, Windows/macOS/Linux without new dependencies.
