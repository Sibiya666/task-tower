## Intent, ownership and limits

Automatically turn an authorized delivery into independently accepted specification, development and testing stages and a reviewable PR. Each role is a fresh process/instance; no executor approves its own work. A saved installation policy, durable host state and validated artifacts control transitions. Model prose, editable cards and GitHub metadata never grant stage acceptance or publishing authority.

Python 3.11+ standard library only; portable core with current Windows native execution qualification (see the release scope amendment). Reuse the installed Codex/custom executable, private connections, executor profiles and pinned Superpowers instructions. Do not install dependencies, select a model, grant credentials/scopes, create a service or change repository protection. Worktrees isolate files, not OS privileges. Trusted custom programs retain the user's existing OS access. Removing token environment variables does not prevent access to other accessible credential stores.

Issue #16 includes a real chat-independent local watch process, automatic transitions, two bounded local task slots by default and automatic refill from the saved backlog. A user can start this CLI through an existing supervisor; installing or configuring an OS startup service is outside this change. The active chat is not the runtime. #18 adds general groups/capacity and richer conflict scheduling; #19 adds distributed ownership. Local SQLite is never a cross-host lock. #16 creates the PR because Issue #16 explicitly requires it; #17 owns PR intake, exact-head/base acceptance, serialized merging and the main/postmerge barrier. #16 never merges, closes an Issue or declares task done.

MVP simultaneous actions are supported across different repositories. Linked worktrees in one repository share Git refs, so the journal atomically permits at most one preparing, role, check, checkpoint or publishing action in that repository; unknown ownership also blocks another action there. Both watch and public work --once enforce this guard. Ready-first scheduling may finish an existing same-repository run before admitting another; two slots do not promise two simultaneous same-repository agents or fair stage interleaving. Preserve the full Git-ref mutation guard rather than silently excluding other refs. General same-repository concurrency and richer scheduling belong to #18.

The coordinator's design choices below are implementation rulings under the existing delegated routine-choice policy, not newly asserted human preferences. Use a dedicated pipeline journal and adapter. Preserve the existing executor v1 configuration, v2 queue and CLI unchanged; do not make both journals owners of one execution. Reuse its primitives through additive internal APIs. Test executors are evidence-only; they cannot silently edit the product accepted in development.

## Private policy and CLI

Every command takes `--connections PATH --journal PATH`. Adapter/work/watch additionally require `--config PATH --executor-config PATH`; watch also requires `--dispatch-config PATH --dispatch-journal PATH`. These are private absolute paths outside every connected checkout, mutually distinct, checked for symlink/junction/hardlink and sidecar aliases using existing private-path rules. A pipeline journal cannot be an executor or dispatcher DB. No automatic schema migration, destructive reset, journal deletion or lease reset is provided.

Pipeline configuration is strict JSON, duplicate keys rejected, no extra keys. Required top-level keys: `version` (integer 1), `tasks` (list). Optional defaults: `max_active=2` (1..2), `interval_seconds=5` (1..60), `task_timeout_seconds=7200` (1..86400), `role_timeout_seconds=900` (1..3600), `max_reworks=2` (0..5, per target stage), `max_processes=36` (6..100), `log_max_bytes=1048576` (1..67108864). Booleans are not integers. Effective timeout/log limits are the minimum of pipeline and referenced executor-profile limits. A task budget starts at its first claim and includes checks, rework, preparation and publication; persisted UTC deadlines cannot be extended by restarting. Within a live process use monotonic elapsed time; backward clock movement fails closed. process_count counts managed model/custom role and configured check launches. Fixed host-control helpers are separately bounded by controller concurrency and the existing task deadline; they cannot renew that deadline or erase attempt counts. This is a time/process budget, not a promise of a dollar/token cap.

Each `tasks` row has exactly `repository`, `issue`, `task_id`, `runner_label`, `executor_profile`, `components`, `allowed_paths`, `spec_path`, `plan_path`, `evidence_dir`, `checks`, `ci_substitution`, `publish`. Repository-qualified identity must match one existing executor allowlist row, profile and private ProjectConnection. The row's repository/Issue/task triple is the explicit private publication mapping; never infer another mapping from Issue prose, a PR title or a model result. `components` is a nonempty duplicate-free list of installation-owned strings matching `[A-Za-z0-9][A-Za-z0-9_.-]{0,99}`; `*` is allowed only as the sole item and conflicts with every task in that repository. Declare uncertain or coupled ownership as `*`. Matching repository/component keys exclude overlap, including unknown owners. Different repositories do not share component locks. This conservative local exclusion is not #18's general scheduler.

`allowed_paths` is a nonempty list of relative POSIX directory prefixes ending `/` or exact relative files. Reject absolute, traversal, backslash, NUL, `.git` and overlapping aliases. Every new/changed/deleted product path must match a prefix/exact entry. Spec/plan and evidence paths must be separately within this allowlist; evidence_dir must end `/` and contain neither spec nor plan. Source policy and test argv come exclusively from the private installation, never model output or Issue prose. `checks` is a nonempty list of strict `{id, argv, timeout_seconds}` rows: unique IDs matching the component regex, nonempty argument arrays, absolute approved executable in argv[0], no shell substitution, timeout 1..3600. Commands run at the worktree root with a private writable temp directory; no model-generated command is executed. A `.cmd`/`.bat` requires an explicitly configured native interpreter as in existing executors.

`ci_substitution` is exactly `{enabled, required_platforms}`. Default is `{enabled:false,required_platforms:[]}`. If enabled, platforms must be a nonempty unique subset of `windows,macos,linux`; reuse authoritative GitHubSource evidence for the exact checkpoint/head with every required check successful. It may substitute unavailable reviewer-local test execution, never a failed host test or failed product test. Record `execution_local=false`, exact CI identity/platforms and the limitation. Read-only reviewers must distinguish unwritable temp from product failure; otherwise return needs_input. No automatic fallback inferred from prose.

`publish` is exactly `{enabled, remote, base_ref, publisher_account}`. `enabled` is Boolean; `remote` is `origin`; `base_ref` is `refs/heads/main`; publisher must match an existing trusted publisher on the connection, and task ID/Issue must match this private task row and its existing executor allowlist binding. Disabled publication stops at `ready_for_pr`, visible as a required policy action, with no remote write. Enabling it is a policy change requiring fresh input validation; it does not grant a new credential scope. The configured Git remote must resolve to this connected GitHub repository; reject a different owner/repository, push URL or ambiguous remote before publication.

Commands:

`work --once` performs at most one role/checkpoint/publication action. `watch` repeatedly performs bounded dispatcher admission and stage work, with up to max_active concurrent task worker subprocesses, and fills a freed slot without a chat prompt. It does not spawn model roles directly; workers own them. Children use argument arrays and remain contained by the existing process runner. Only fixed trusted host CLI worker and dispatcher-helper subprocesses may inherit existing GH_TOKEN/GITHUB_TOKEN for host API authentication, including environment-only installations. They never put credentials in arguments, request/result JSON, configuration, logs or artifacts. Model, custom adapter and configured check children retain case-insensitive token stripping through child_environment; a trusted host worker must never forward its raw environment to those children. Existing safe Git child filtering and separate Git transport authentication remain unchanged. This distinction grants no scope and stores no credentials. Watch catches Ctrl-C, requests cancellation of owned workers, waits at most five seconds for cleanup and records uncertainty instead of claiming success. Existing dispatcher default source factory and genuine `verified_done` remain in use.

Status/cancel/inspect require a still-connected repository and valid journal paths, but do not require a current executor profile or valid pins. Revocation must not prevent inspection/cancellation. `reconcile --inspect` is read-only: reports persisted intents and positive observations; it never reruns a role, retries POST/push, kills an arbitrary PID or clears fencing. Successful observations may be consumed by the live matching owner before it records completion; after owner loss unknown effects remain fenced for explicit future reconciliation functionality, with a concrete required action. Do not ship a recovery command that merely changes unknown back to ready.

Public JSON uses fixed statuses/reason codes, identities, timestamps, hashes, counters, CI/PR URLs and relative artifact names. Never emit private absolute paths, raw argv, prompts/logs, summaries or exception strings. CLI returns 0 for a completed bounded tick/status/valid durable admission, 1 for operational uncertainty, and 2 for invalid policy/state. A task needs_input is a visible parked outcome, not global watch failure. Logs/reports stay bounded.

## Canonical checkpoints and acceptance bindings

Pipeline product text scheme `sha256-utf8-lf-v2`: decode strict UTF-8, preserving an optional UTF-8 BOM as the leading U+FEFF content; replace CRLF and bare CR with LF, then encode UTF-8. Preserve all other content/whitespace, including final newline presence. `canonical_text(data:bytes) -> bytes` performs this pure conversion without rewriting the source file. BOM presence changes the digest; a BOM-bearing PowerShell file and its BOM-free counterpart are different inputs. Existing `overlay/*.ps1` intentionally use BOM for PowerShell 5.1 Cyrillic and must retain it. Persist canonical input copies privately, never normalize checked-out product files as a hashing side effect. This new pipeline scheme has a new name because existing `tasks._hash` `sha256-utf8-lf-v1` preserves BOM but normalizes only CRLF; do not redefine that legacy scheme, recalculate old receipts under v2, or change existing instruction-pin canonicalization.

`canonical_artifact(data:bytes) -> bytes` first rejects BOM, then applies canonical_text. It is for newly machine-generated spec, plan, criteria and MD evidence; these required artifacts must be BOM-free strict UTF-8. Existing product text outside those designated artifact paths may contain BOM. Classify a product blob as text if strict UTF-8 decoding succeeds and it contains no ASCII controls other than tab, CR and LF; preserve a leading U+FEFF. Nontext blobs, including valid UTF-8 with binary control bytes, use raw SHA-256 labeled `sha256-bytes-v1`. Record the scheme per path; neither binary assets nor BOM text may be silently excluded. JSON manifests use sorted keys, separators `(',', ':')`, ensure_ascii=True, allow_nan=False and BOM-free UTF-8, no trailing newline for hashing. Instruction pins retain existing profile canonicalization and manifest digest behavior. Test LF/CRLF/mixed-CR, content changes, BOM-bearing PowerShell LF/CRLF equivalence, BOM-presence differences and unchanged source bytes.

Product manifest enumerates sorted relative POSIX paths with `{path,mode,scheme,sha256}` for all tracked and nonignored untracked ordinary files, including additions/deletions relative to initial source. Bind executable mode as Git mode, reject symlinks/reparse points/hardlinks/submodules, unsafe paths and unexpected external Git directory/branch. Exclude `.git/`, the exact configured evidence_dir and known mutable `docs/tasks/*.json` cards only; do not exclude arbitrary `docs/`, tests or all Markdown. Spec and plan are separate accepted artifacts and remain product files. Any mutable-card diff is rejected rather than silently published. Evidence_dir changes may contain only host-generated projections; preexisting or model-modified evidence fails closed. Omit ignored files from publication and reject newly created ignored output presented as required evidence. Bound each designated spec/plan/criteria/MD-evidence artifact to 1 MiB; this is not a general source-file or binary-asset cap. Bound every other ordinary product blob, text or binary, to 16 MiB, covering the current Task Tower image/source assets without silently dropping them; hash binary blobs incrementally. Bound the product manifest to 100,000 paths and 16 MiB. Check raw and canonical artifact lengths against their respective cap; exceeding any limit parks needs_input with a fixed size_limit reason and the relative path/limit, without truncating accepted input or rewriting/excluding the file.

Freeze each role output after successful exit/cleanup and validation, inspect allowed-path diffs, then construct a host-owned private Git index and checkpoint commit on branch `pipeline/<run_id>`. Use exact initial source SHA from profile source_ref and verify it before creation/launch. Host Git hooks are disabled with an empty private hooks directory; use fixed host-generated commit messages and no shell. Record intended parent and tree OIDs before commit/ref update, then check actual commit/tree/parent and branch ownership. No model-supplied SHA or direct commit is accepted. Model roles must not commit, push or create PRs; an unexpected HEAD/ref change fails closed, preserving worktree. Product snapshot freezes before reviewer launch; reviewers inspect a separate detached checkpoint worktree and never the mutable executor worktree.

Stage input manifest is exactly `{version:1,repository,issue,issue_id,task_id,run_id,stage,generation,source_sha,base_sha,checkpoint_sha,product_sha256,criteria_sha256,spec_sha256,plan_sha256,prior_verdict_sha256,policy_sha256,superpowers_sha256,checks_sha256}`. Nullable not-yet-produced spec/plan/prior/check values are JSON null. `source_sha` is immutable initial source, `base_sha` is the initial authoritative main SHA, `checkpoint_sha` is the host-frozen current checkpoint, and product/spec/plan hashes bind current accepted content. `checks_sha256` is null before tests and the host-generated check-manifest digest for test review. Store the manifest before launch; `input_sha256` hashes it. Never include its verdict, mutable status, final evidence projection or the manifest itself in product inputs. Every prior-verdict link is to an already persisted immutable receipt; no self-reference.

Acceptance receipt includes this full manifest and digest, stage/generation, executor_instance_id, reviewer_instance_id, reviewer attempt ID, instruction/policy digests, validated result digest, process/cleanup evidence and fixed decision. Fresh host-generated UUIDs identify every role invocation; reviewer ID differs from all contributing executor IDs and previous reviewers, and its role must have been launched by the host with that exact manifest. A supplied different string is insufficient independence. This is trusted host attestation, not cryptographic proof against a malicious OS user. Rehash checkpoint, artifacts, criteria/policy and prior acceptance immediately before persisting a verdict and before advancing. Reject stale responses even if their JSON says approve.

## Watch, recovery and observations

Only one local watch controller holds its journal owner at a time; multiple work processes still use atomic claims. Owner liveness checks reuse the executor positive-death approach under a claim/recovery exclusion transaction. Live, PID-reused or unprovable ownership is never stolen. Positive owner death changes unfinished action to unknown; it does not prove descendants exited, free capacity or authorize replay. Restart may continue a ready run only if all prior actions have positively durable completed evidence and no incomplete intents. Repeated normal watch ticks must never rerun a completed role.

Each watch tick reloads and validates saved connections/policies, checks cancellation/deadlines, recovers positive-dead owners conservatively, polls owned workers, invokes existing dispatcher.tick at most once and fills free eligible task slots. Persist tick health and neutral reason codes. Normal interval is five seconds.
