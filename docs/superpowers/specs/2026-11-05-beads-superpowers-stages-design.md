## Intent and evidence baseline

Deliver a bounded foreground Windows coordination session which takes explicitly authorized, canonically ready Beads work through mandatory SPEC, DEV and TEST, each with a distinct independent acceptor. Preserve genuine source and process evidence and hand a tested candidate to the separate PR/main/closure barrier. A blocked task must not stall unrelated authorized ready work. Continue the authorized backlog when a completed acceptance cycle releases a slot, without asking for another chat continuation.

Beads/Dolt remains the sole task, dependency, claim and history authority. Task Tower supplies fixed host integration, supervised role execution and artifacts; it does not create a second graph, queue, claims table, SQLite stage database or controller journal. Active-chat coordination currently implements the operator's development policy. The proposed foreground session is a component of future local delivery, not a persistent background agent pool.

Accepted base is `ab91f551fb10e18622e2251e7d4709a2f2c380fb` (PR84). Its public component receipt records admission acceptance, exact-main tests and closure by the coordinator; it explicitly records `task2_stage_execution:false` and `unattended_ready:false`. The [admission design](2026-11-05-beads-admission-design.md), [operator documentation](../../beads-admission.md), [backlog](../../backlog.md) and repository AGENTS are prerequisites. Admission observations are inputs to revalidation, never claims.

Source inspection establishes these reusable boundaries:

- `task_tower/harness.py` prepares interactive launch instructions and explicitly advertises no structured events, resume or independent review. Supplying a Superpowers path does not prove execution.
- `task_tower/executor_harness.py` has shell-free invocation and strict result helpers. Its old role binding/generation schema and pipeline input imports belong to historical implementation. Do not import the old controller or revive its profile/journal/claim ownership. These are process primitives, not task acceptance or restart recovery.

No old worker, pipeline/group runtime, historical receipt, Books settings, Codex log or private database is an input to this design.

## Scope and chosen shape

The smallest coherent increment is one foreground, operator-started Windows session with an interim ceiling of two independent claimed tasks and two concurrently running role/check processes, following current active-chat policy. This is a conservative delivery bound, not permanent product capacity: `.4` owns configurable capacity/budgets and the user's preference to use available capacity. No new capacity configuration is required here. There is one active role per task. The session retains live process handles and transient coordination state only in memory. Native Beads task history records stage events and artifact references. Private immutable files retain bounded evidence, but are never executable state or a recovery journal.

Builder choices proposed here, rather than assertions of user selection: Python 3.11+ standard library, reuse the existing Windows process supervisor, a process-scoped OS exclusivity guard for the configured local project, and an explicit stage-session entry point separate from Books/admission. The eventual plan selects names and file boundaries. Do not register a Windows service, scheduled task, autostart entry, HTTP endpoint or watchdog. This design adds no installation, model, account, auth, scope or global harness configuration change.

An exclusive local project session prevents two Task Tower writers on this one embedded installation; it does not exclude an external Beads client or imply distributed locking. Fixed Beads writes are serialized even when role execution is parallel. A native claim is still mandatory. A lost/abandoned exclusivity guard never restores prior task ownership.

Two task slots are independent only when repository identity, dependency graph, worktree, branch and semantic ownership permit it. The coordinator records proposed owned paths and behavior in each task's native history before dispatch. Overlapping behavior or an ambiguous shared integration contract is serialized, even if paths differ. An executor may not edit another task's worktree. Coordinator-only reconciliation invalidates affected stage evidence. A task waiting for input retains its canonical claim and evidence, launches no role and does not monopolize the other slot. Unknown cleanup additionally fences the affected project/worktree; unrelated work is allowed only if isolation can actually be proved.

## Native Beads primitives: what is established

The allowed captured public help is for installed Beads 1.3.4. Root help lists `ready`, `show`, `history`, `comment`, `note`, `provenance`, `state`/`set-state`, `gate`, `heartbeat`, `reclaim`, `unclaim` and `merge-slot`. A command name does not establish its JSON schema, atomicity, permission semantics or lease behavior.

Installed `update` help explicitly documents `update ID --claim`: atomic assignment to the actor and transition to `in_progress`, idempotence for that same actor, and special configured pool aliases. Guarded updates (`--if-assignee`, `--if-status`) cannot be combined with `--claim`; guard mismatch exits 13. Multi-ID updates are not atomic. Therefore use exactly one qualified, policy-allowed ID per claim; never use force, pool admission, reclaim, unclaim or an assignee overwrite to manufacture success. Generate a fresh session actor within the operator-approved actor namespace so same-actor idempotence cannot adopt a prior session's claim. The currently claimed development task is not a reusable product execution lease.

Installed `ready` help additionally documents blocker-aware `GetReadyWork` semantics and `ready --claim --json`, which atomically claims the first ready issue matching filters. This is stronger than separate ready/read and `update --claim`. Its documented filters have no exact issue-ID option: labels, metadata, parent or molecule can match an unauthorized alternative. Never claim broadly and then undo an unauthorized result. The selected-ID route therefore uses `update ID --claim` plus conservative postclaim native checks; it does not claim transactional dependency readiness. A filtered native ready-claim route is allowed only when the complete possible match set is provably policy-authorized and semantically reserved before the write, not merely because a current ready snapshot contains one row. Do not invent `ready --id`, mutate labels to manufacture proof, or treat metadata/parent membership as authorization. Refuse broad native claim when that precondition cannot be established. The coordinator's actual administrative claim of this development task is separate and is not rewritten as ready-claim.

Installed molecule help establishes native protos as template DAGs and `mol pour` as persistent instantiation. Formulas, molecules and gates are preferable to a replacement workflow database if durable stage subissues are later required. For this increment, keep one original canonical task and stage events/references through its supported history interface; do not pour speculative stage cards, squash/burn history, duplicate dependencies or introduce a parallel stage graph. Installed `set-state` help explicitly promises atomic creation of an event bead (source of truth) and replacement of the dimension label (lookup cache); `state` reads that cache. Prefer this native event mechanism for host stage projections once its bounded event-readback schema is established. Labels remain neither acceptance evidence nor an executable scheduler. Native merge-slot evaluation belongs to `.3`; its name alone cannot prove the required main barrier.

Use an installed-version contract test before selecting exact history commands. Prefer `set-state ID tower-stage=VALUE --reason SAFE_REFERENCE` with fixed dimensions/values and independently validated event readback; the reason carries a sanitized host event reference/digest. `update ID --append-notes` is explicitly documented as append rather than replace and is a fallback if native event readback cannot retain the needed references without extra task graphs. Serialize each bounded host event and verify through public Beads reads/history. A timeout after a possible write is unknown, never an automatic retry. No raw SQL, direct Dolt/database access, settings change or new storage engine is permitted.

## Admission, claim and effect ordering

1. Hold the live local exclusivity guard. Load separate operator authorization, not Books configuration. Require the configured repository/project/allowlist, actual base SHA/tree, supported clean source and existing admission path/environment protections. Enumerate only bounded native ready results; choose an allowed executable task using stable returned priority/ID order, never task prose or Markdown files. Overflow refuses rather than silently hiding work.
2. Re-run admission immediately before the write. Record a new host session/run identity and proposed isolated worktree/branch/semantic ownership. Source checkout effects and role launch have not occurred yet.
3. Claim exactly that task through the native atomic operation under the fresh actual actor, with bounded capture and no shell. Require successful exit, complete output, confirmed cleanup and canonical readback matching task/project/actor and `in_progress`. Failure or ambiguity prevents all task effects. A successful readback alone cannot erase an uncertain claim process outcome.
4. Recheck source, authorization and the supported canonical postclaim dependency contract before creating the isolated worktree or launching a role. Use fixed bounded public `show --id=ID --brief-deps --json` and `dep list ID --direction down --json` to verify identity, owner and canonical dependency facts. These flags are documented in installed help; precise JSON fields and full blocker/gate semantics require an installed-compatible schema/fixture contract. Unsupported, missing or changed facts fail closed. A readiness observation followed by atomic ownership is not an atomic readiness-and-claim transaction. External task/dependency changes invalidate admission; see the contract check below. Refuse execution when the installed interface cannot establish supported postclaim eligibility.
5. Append and verify the host start event before launch. A launch-intent event is not proof of launch. Bind every subsequent role to this live session, native owner, task, source and exact stage input. Recheck owner and pinned inputs before each launch and acceptance, and after role completion. Changed owner/policy/source stops advancement.

Native readiness continues to own dependency evaluation; do not replace it with an application DAG scheduler. Fixed, bounded public queries may verify canonical facts under an established supported contract, but a guessed interpretation of dependency JSON is forbidden. Role output and task descriptions cannot supply commands, credentials, permission expansions or Beads mutation instructions.

## Mandatory stage contract

Each task uses six fresh role instances: SPEC author and SPEC acceptor, DEV implementer and DEV acceptor, TEST executor and TEST acceptor. Every acceptor is distinct from every executor and the other acceptors for that task, with a fresh context/process identity. Role labels or different prompt text do not prove separation. Only the host assigns instances and starts them through a configured, explicitly approved installed harness contract. Sharing the approved model is allowed; reusing an executor conversation as its reviewer is not.

| Stage | Executor artifact and behavior | Independent acceptance barrier |
| --- | --- | --- |
| SPEC | Apply installed pinned Superpowers brainstorming and writing-plans; create the bounded design and implementation plan, criteria, ownership and verification selection. No product code before full description approval. | Fresh builder/SPEC review reads actual task, constraints, design and plan. Requirements and material API gaps must be resolved. Human decisions outside existing authorization remain user questions. |
| DEV | Follow accepted plan, TDD where applicable, preserve genuine RED/GREEN/check facts, implement only owned behavior, produce source checkpoint and exact diff. Documentation-only changes receive relevant checks rather than artificial TDD. | Fresh DEV reviewer examines the actual whole task diff, criteria, plan deviations, source identity and process evidence. No advancement with blocking findings. |
| TEST | Inspect the real checkpoint and criteria; run the meaningful selected host checks under supervision; supply actual outputs/manifests, exclusions and limitations. Tests cannot claim native/live coverage from fixtures. | Fresh TEST acceptor checks source, test inventory/results, provenance and acceptance coverage. Missing live evidence is stated and can block; a model saying tests passed is insufficient. |

SPEC authoring may need several bounded role calls (design, then plan); each has a fresh attempt ID and host-observed process facts. Approval of the design precedes plan/implementation as required by the selected skill and existing operator delegation. Reject/needs-input preserves findings and returns to the earliest affected stage. No automatic retry loop: at most one corrective attempt per stage per session; further rejection pauses that task for explicit coordination. Any implementation/test repair is a DEV change and invalidates downstream acceptance. A changed specification invalidates DEV/TEST. No executor writes accepted/done.

Acceptors receive a read-only checkout/snapshot and evidence access. TEST executor may need a disposable writable test sandbox for real tools, but cannot mutate the candidate source; rehash before/after and reject unexplained changes. A read-only model role flag alone is not sufficient isolation for a custom adapter. New tests or repairs proposed by TEST return to DEV. Worktree checkpoint creation and safe fixed Git actions are host-owned; task prose is never shell input. Candidate base, source commit/tree, exact diff digest and artifact digests must all be recorded; dirty/untracked content cannot be hidden behind HEAD alone.

### Runtime TDD and corrective input contract

Documentation tasks retain eight fresh role calls and meaningful documentation validation without artificial RED. Runtime tasks need a host-selected nine-call route: the four SPEC calls, fresh tests-only DEV, fresh implementation DEV, DEV acceptor, TEST executor and TEST acceptor. Selection comes from an operator-verified live runtime check capability, never task prose or a model-provided command. Keep the same live role authority and all independent/fresh instance guards. Missing runtime capability refuses before claim; it cannot be described as delivered merely because documentation works.

The tests-only invocation can change solely the operator-attested test subset; host verification proves implementation bytes and protected metadata unchanged, then records the test checkpoint. Execute fixed shell-free selected unittest checks in a qualified disposable sandbox at exactly that snapshot, with actual process/EOF/cleanup and failure evidence. A nonzero exit alone is insufficient RED: fresh independent DEV review must assess relevance to intended missing behavior rather than malformed tests or setup/infrastructure failure. The implementation invocation preserves exact RED test bytes and can change only owned implementation paths. Changed tests invalidate RED and return to a fresh tests-only pass. GREEN repeats the identical selection at the new checkpoint. DEV review examines the whole original-base diff and both source-bound DEV/check chains; TEST executes the authorized full candidate checks before independent TEST acceptance.

Host-generated phase instructions and rejection feedback are immutable registered input files, bound through the existing request artifact pins. Feedback carries the exact rejected source/artifact identities, private findings and earliest affected stage; expose it to the corrective role through qualified individual read-only access. Public native history contains only references/digests. Invalidation removes stale stage approvals, not the findings needed for repair. Registration of these inputs does not grant stage acceptance or command authority.

Per-instance DEV write scope is live host state: `RoleAuthority.register_phase_scope(instance_id, owned_paths)` pins a bounded validated operator-derived subset once, and `get_phase_scope(instance_id)` is a pure memory lookup. A registered scope requires the containment grant's exact write-path tuple; phase instruction JSON supplies no privilege. Tests-only scope excludes implementation, while implementation preserves pinned tests. Refuse configurations whose overlapping positive prefixes cannot express the required narrower scope safely. Existing callers without a phase registration retain their prior contract; runtime dispatch always registers its scope and never resets authority.

## Evidence and genuine provenance

The actual accepted Task Tower checkout produced a complete 721-file source snapshot of 96,624 canonical UTF-8 bytes. It cannot fit inside the existing 64 KiB role request. Preserve that request/result ceiling and the complete host inventory: retain inline snapshots for small inputs, and support `source_manifest: {name, sha256}` as an alternative bounded transport. `name` is a host-generated safe logical input name, never a filesystem path. Resolve it solely through a coordinator-held source-input map, distinct from prior accepted role artifacts.

The referenced input is the complete canonical snapshot in a safe regular nonlinked immutable host file, at most 16 MiB, outside candidate, current role output and private evidence roots. Validate duplicate-free schema, canonical UTF-8 bytes and actual file SHA256, and compare parsed content with an independently recomputed source snapshot before launch. The existing qualification approval still binds the parsed snapshot's internal `manifest_sha256`; its reference file SHA256 is a separate digest. Qualified containment must expose exactly this input read-only, not its parent directory or broader evidence. Rehash the immutable input after completion and preserve existing non-DEV immutability and legitimate owned DEV delta checks. Missing, stale, altered, unsafe, oversized or unqualified references refuse; no reference JSON supplies authority or permits omitted files.

Extend the admission vocabulary rather than importing historical envelopes. A host event binds schema/kind, qualified task identity, session/run/attempt/role-instance IDs, actor, stage, policy/input/Superpowers pins, source commit/tree and diff digest, earlier accepted artifact digests, observed process facts and bounded relative artifact names plus SHA256. Acceptor events additionally bind exact reviewed artifact/source sets and their own process instance. Pin both candidate and base; a changed base invalidates dependent code acceptance pending re-evaluation.

Store role-produced files separately from host evidence. A fresh private host-owned evidence directory is outside worktrees and private configuration. Children receive only the bounded role request, permitted source and role output location; no host evidence write access, Beads credentials/directory, tokens or configuration. Strip GH_TOKEN/GITHUB_TOKEN case-insensitively, preserve existing environment/path protections and do not expose private paths or raw streams in public Beads history. Safe public events contain fixed reason codes, digests and references; source prose/raw logs remain private unless explicitly reviewed for publication.

Host provenance comes from live supervisor results plus actual input/source/artifact hashing and independent instance observations, not the validity of model JSON. The host reads role output only after known process completion, EOF and cleanup, applies strict bounded duplicate-key rejecting schemas, independently hashes safe nonlinked artifact files, and issues its own completion/acceptance event. A forged `accepted` field, copied result, stale ID, edited manifest or standalone receipt never advances the stage. The model verdict is one input; the host must verify its bindings and process/source conditions.

Artifacts are immutable evidence, not an authority store. Beads history is the canonical record of what occurred. A missing or uncertain history append blocks that task; do not replay the append or infer success from a local file. At restart, even apparently valid native history and artifact hashes cannot establish the old process/claim fence. This increment deliberately offers no receipt adoption or automatic resume.

## Lifecycle, bounds and unknown outcomes

Native contract qualification observed a five-minute claim lease and an owner-only `heartbeat` command. Maintaining this native lease is a basic execution prerequisite in `.2`, not the configurable health/recovery feature of `.4`. Renew current-session live claims every 60 seconds on the coordinator's serialized Beads lane, with renewal deadlines taking priority over other writes. Role execution must not hold that lane. Qualify successful heartbeat completion and bounded owner/status/expiry readback; require actual EOF/cleanup and verified lease advancement. Heartbeats update Beads' node-local ephemeral lease table without Dolt commits/history, so they are not durable stage evidence.

Track a conservative monotonic lease-expiry budget and reserve operation plus cleanup time. Prevent effects and cancel/reap owned live processes before expiry if safe renewal cannot finish. Lost ownership, expired lease, or unknown heartbeat/readback fences the task; never retry an uncertain renewal or revive expired/prior-session ownership. Cancellation callbacks read cheap in-memory cancellation state only: no Beads, database, Git or subprocess calls inside `cancel_requested`.

Start is explicit and foreground. Stop/cancel prevents new claims/launches, requests supervised cancellation, kills/reaps the owned Windows job tree and waits for stream EOF within the existing five-second cleanup deadline. Only host-owned live handles authorize termination; never kill a PID recovered from JSON/history. A crash closes job handles and should kill descendants; native crash tests must prove this rather than assuming the Windows flag is sufficient.

Proposed conservative fixed interim ceilings for `.2`: two task slots, two active supervised role/check processes, serialized Beads writes, 30 seconds per admission/Beads operation, existing 10-second local Git limits, 30 minutes per role attempt, eight hours per foreground session, 8 MiB captured prefix per stream, 64 KiB request/result/event JSON and at most one correction per stage. Ceiling exhaustion stops that task/session safely, preserves evidence and never marks completion. `.4` owns configurable capacity/budgets/health, including use of available operator-approved capacity; these initial safety bounds cannot be postponed and do not establish permanent capacity. Captured prefixes or unknown EOF are never complete transcripts; hash/byte counts retain their actual meaning.

Unknown claim/write/launch/completion/cleanup/history outcome has no automatic replay, retry, release or reassignment. Leave the canonical task claimed/fenced, report sanitized uncertainty and stop affected effects. A fresh process refuses prior-session claimed tasks, even when the operator actor looks similar; no `reclaim`, lease expiry or timestamp converts them to safe work. Reconciliation is an explicit operator action with independently established process absence and native history, with broader recovery deferred to `.4`/`.5`. Cancellation with confirmed cleanup is still not successful delivery and cannot close the task.

The local foreground session may continue an already independent second task after a known per-task needs-input result. Loss of project authority/exclusivity, unknown shared process ownership or unknown shared integration outcome stops the project session. No persistent background execution claim follows from a successful foreground test.

Cancellation must reach native Beads/Git supervision and source enumeration/hash work, not just the model worker. Preserve actual native process EOF/cleanup facts through unsuccessful port outcomes. Check stop before renewals and new effects. Cheap exact Event checks between operations and hash chunks, together with supervisor cancellation, preserve the existing operation limits and five-second cleanup contract; unknown proof retains project exclusion. Extending the existing admission runner with an optional Event preserves current read-only callers and avoids duplicating supervision. No cancellation callback performs Beads, Git, database or other external work.
