## Connection contract

Python 3.11+, standard library, Windows/macOS/Linux. Add an explicit project-first onboarding command and bootstrap flags; local-only harness launch remains available and must not claim GitHub readiness. Existing credentials come from environment/gh/git; never log/store tokens or silently authorize more scopes. Missing Projects access yields actionable needs-setup/error and zero Issue POSTs. Resolve repository/owner identity through authenticated GitHub APIs. Reuse an explicitly supplied Project URL or the sole suitable linked Project. More than one candidate is ambiguous and requires explicit selection. If absent, find a matching owner Project from bounded pages and link it, or create a repository-linked Project. Validate owner/repository association and write access. Existing unrelated boards remain untouched. Setup repeated with the same identity must not create another Project or lose another connection. Unknown creation responses reconcile existing owner/linked projects; do not blindly create after an unknown outcome.

Configure a Status field/mapping for open, in_progress, awaiting_merge, awaiting_postmerge, postmerge_review, postmerge_failed, needs_input and done. Preserve existing configured fields/options; create missing managed states without deleting other options or items. Store Project URL/node ID/field/option mapping only in private connection config, using safe atomic writes and conflict detection. Invalid config, unsafe symlink/reparse paths or concurrent changes must not overwrite user data. The repository contains examples/placeholders and its own development docs, never a user's connected-project list.

## Reconciliation and identity details

- Use the authenticated repository node ID and canonical owner/name for discovery and linkage. Resolve user versus organization ownership through the API, not URL spelling alone. Supplied Project URL, returned Project node ID, owner and stored mapping must agree. An existing connection ID may update its own same-repository setup, but must not silently retarget another repository or replace a different connection's identity.
- Exhaust the bounded linked/owner discovery before concluding absence or uniqueness. A page limit, partial GraphQL errors or inaccessible candidates is an incomplete result, not permission to create. A title match alone is not repository identity: only reuse an unlinked owner candidate when its deterministic expected identity is unambiguous; otherwise require an explicit Project URL. Do not change Project visibility.
- A timeout or malformed/partial mutation response is an unknown outcome. Re-read authoritative state to reconcile creation, linkage, membership and field changes. If the outcome cannot be uniquely established, return actionable needs-setup with known IDs/URLs and stop; never blindly repeat a create. Concurrency across independent hosts is not solved by discovery; this milestone must not claim distributed exactly-once creation.
- Preserve existing field/option IDs and labels and all unrelated options/items. Refresh and verify the actual field/options after mutation before persisting the mapping; do not assume returned IDs survive an option update. An incompatible field type, ambiguous managed option or inability to preserve an existing field fails visibly instead of replacing it.
- Snapshot and validate private configuration before remote mutations. Commit through a conflict-detecting atomic writer; simultaneous Task Tower writers must not both pass a check then overwrite one another. On a conflict or local write failure after remote success, retain remote resources, report the Project URL and rerun instructions, and do not publish a ready connection. Never roll back by deleting a Project or Issue.

## Issue creation and recovery contract

Before any new Issue import, require a configured, available, writable Project linked to the same repository and a complete usable status mapping. A bare URL is insufficient. Missing access or incomplete setup stops before Issue POST. Existing ordinary read-only connection/book commands remain compatible but are documented as not fully onboarded for creation.

After creation, add the Issue to its Project and apply mapped status. If membership/status fails after Issue creation, retain the Issue and expose a retryable partial result. Retrying finds the same legacy ID and repairs membership rather than creating another Issue or overwriting description. Reusing an existing Issue also repairs membership. Do not treat arbitrary closed Issues or metadata done as independent acceptance; retain existing proof verification and default denial.

Resolve task identities within the authenticated repository only, using complete bounded Issue enumeration. Match the imported card's ID against explicit Task Tower metadata `task_id`, `legacy_id` or legacy `id`; existing Issues 13-28 use `task_id` and must be reused. In particular, `TT-PROJECT-ROLLOUT-001` reuses Issue 24. Multiple matching Issues, conflicting aliases within a matching record or incomplete enumeration block creation and need explicit repair. An unknown Issue POST outcome follows the same reconciliation rule: find its exact task identity marker, repair one unique match, otherwise stop with an uncertain result rather than issuing another POST. A visible partial result includes the Issue URL/number and the failed setup or membership stage. Repair must preserve prose/evidence and must not regress an existing authoritative lifecycle state to the imported card's old status. A fresh board check is a preflight, not a cross-API transaction: permission loss after it is a partial failure to recover, not grounds to delete the Issue.

The first-run path must be usable through the installer/bootstrap and a CLI connection command. It does not implement autonomous development, background PR intake, groups or nightly execution; capabilities and documentation remain explicit about those limits.
