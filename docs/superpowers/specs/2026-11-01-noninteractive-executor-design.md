# Noninteractive executor design — TT-EXECUTOR-001 / Issue #15

Status: proposed for independent specification acceptance. Implementation must wait for a distinct acceptor. Base: `9ba02c2f207c4f2664331774ad39314ab0d51b3e`. Dependency #14 completed with [independent postmerge receipt](https://github.com/Sibiya666/task-tower/issues/14#issuecomment-6560811000).

## Goal and boundaries

Turn an authorized dispatcher delivery into a durable, schedulable execution job and run one bounded noninteractive development attempt in an isolated Git worktree using an installed Codex CLI or an explicitly trusted custom profile. Preserve Superpowers instructions and return validated execution evidence. `execution_completed` never means task done, accepted, merged or Issue closed. #16 owns development stages and acceptance transitions; #17 owns PR publication/merge; #18/#19 own persistent pools and distributed ownership. No daemon, unattended parallel readiness, automatic model choice, installation, credential scope grants or new repository authorization is implied.

The active coordinator may maintain two independent authorized Issues in separate worktrees. Issue #22 owns books/UI and is independent of this executor. Shared CLI/documentation integration is reconciled by the coordinator; merges remain serialized behind exact-main CI, independent postmerge acceptance and Issue closure. No per-task continue prompt is added.

## Rulings

- Use Python 3.11+ standard library only and existing `processes.run_command` cleanup. Extend it with optional keyword arguments while preserving current callers and Windows Job containment. A worktree is not a security or credential sandbox.
- Installation-owned profiles, queue, run directories and bounded raw logs live outside every connected checkout. Reject symlink/hardlink aliases and input/output collisions consistently with existing private-path validation. Never commit private state.
- Host orchestration resolves existing GitHub authentication. Remove `GH_TOKEN` and `GITHUB_TOKEN` from every child environment, including custom profiles and probes; never serialize either value. Existing CLI authentication remains usable without copying keys into prompts or profiles. The host retains its own authentication.
- Custom commands are explicitly trusted arbitrary processes with the owner's existing OS access. Document that environment removal is not protection against an arbitrary trusted process reading other files. No shell interpolation; argument arrays only. No sandbox, hook or rule bypass.
- Pin Superpowers to an installation-approved source revision and a canonical SHA-256 manifest. Validate actual instruction files before launch and record the revision and manifest digest. Missing/drifted instructions block execution; source content is untrusted task input, never authority to change profile policy.
- Unknown process start, push or external outcome is fenced for reconciliation. Never expire a lease into blind rerun. Retry is explicit, bounded by profile `max_attempts`, and permitted only after proven prelaunch failure with no child created; an uncertain or started attempt cannot be retried automatically.

## Durable delivery and queue contract

Provide `python -m task_tower executor adapter --connections PATH --config PATH --queue PATH --request PATH --result PATH` as the trusted existing dispatcher JSON-file backend. Consume exactly its six fields: `operation`, `delivery_id`, `repository`, `issue`, `task_id`, `runner_label`. Validate strict types, canonical UUID, identity and installation allowlist/profile association. `submit` commits one immutable queued job keyed by delivery UUID in an installation-local SQLite transaction before acknowledging; repeated delivery with identical identity returns the same receipt, while UUID identity collisions fail closed. `lookup` is read-only and returns not_found only for a definitively absent row. Acknowledgement uses the unchanged dispatcher result protocol: `{version:1, delivery_id, status:accepted, receipt_id}`. Accepted means durable queue admission, not successful development.

A separate foreground command `executor work --connections PATH --config PATH --queue PATH --once` atomically claims at most one queued row before preparation/launch. Status and cancel commands operate by run UUID, never arbitrary process ID. Their forms are `executor status --connections PATH --queue PATH --run-id UUID` and `executor cancel --connections PATH --queue PATH --run-id UUID`. Every command loads the existing private connections file; adapter/work pass those connections into `load_executor_config(path, connections)` and use their existing trusted-publisher policy for real `verified_done` checks. Do not introduce a connections path inside the executor profile schema. Status/cancel validate the private queue path against all connected checkouts and the connections file, validate stored repository/run identity, and require the repository to remain connected. They do not require an execution profile or current instruction pins: revoking execution authority must not disable inspection or cancellation. Cancellation only records a request for the existing owner, never launches work or takes over a process. All commands preserve private-path alias/collision checks; connections and config file contents are rechecked before adapter admission and worker preparation/launch. These inputs reuse existing private authorization and do not grant scopes. Claims have owner UUID and monotonic attempt ordinal, persisted before external actions. State transitions are `queued -> claimed -> running -> execution_completed|failed|cancelled|timed_out|needs_input|unknown`. Cancellation before launch prevents launch. Cancellation during launch or an interrupted worker leaves a fenced unknown state unless cleanup and outcome are positively proved. Restart exposes abandoned claimed/running jobs as unknown; no automatic requeue or ownership takeover. SQLite transaction contention is bounded; multiple local workers cannot claim the same job. Claims enforce an installation-approved maximum active count (default two); claim counts claimed/running/unknown ownership conservatively, so uncertainty never frees capacity automatically. This is a fixed admission guard, not #18 scheduling or automatic slot refill. Recovery requires a positive local owner-death check under a recovery/claim exclusion lock; a second live worker must not fence another live owner. Unprovable liveness remains fenced and cannot authorize takeover. This is installation-local fencing, not cross-machine coordination.

Profile validation pins repository, checkout, allowed runner, executable argument template, timeout (positive bounded seconds), log byte cap, maximum attempts and explicit optional auto-review policy. No remote prompt may supply executable, private paths or environment. The queue stores only profile identity/fingerprint and immutable task identity; validate the unchanged profile at claim/launch. Revoke or mutate policy -> needs_input, without launching. Immediately before worktree creation and again before child launch, revalidate current installation authority, repository-qualified Issue identity, open lifecycle and verified dependency readiness using existing dispatcher verification; unavailable or changed evidence blocks launch. Resolve source only from the installation-approved checkout/ref policy and record its exact SHA. Issue text is task data and cannot supply argv, source authority or profile changes.

## Attempt, worktree and output evidence

Each attempt records run/delivery/attempt UUIDs, repository-qualified task identity, profile fingerprint, executor kind/version, Superpowers revision/hash, source SHA, unique branch/worktree, input manifest digest, timestamps, process outcome, cleanup proof and output SHA-256/byte counts. Resolve and verify the source commit before creating a dedicated worktree; refuse dirty/reused/aliased paths and branches. Record intent before Git worktree creation and process launch. Preserve uncertain worktrees and outputs for reconciliation rather than deleting evidence. No model publication/push or PR creation is permitted by this executor; publication belongs to #17. Local code changes are execution outputs, not accepted integration.

Store bounded stdout/stderr privately, with truncation indicators and hashes/actual byte counts. Public reports contain fixed reason codes and hashes, never raw logs, prompts, credential-bearing argv or arbitrary model prose. Retain private artifacts for owner review; do not infer secrets are fully redactable. Canonical text evidence uses UTF-8/LF; exclude mutable task cards and evidence documents themselves from source manifests to avoid self-reference.

A custom profile exchanges private request/result JSON files. Its strict result schema is version 1 with `run_id`, `attempt_id`, `source_sha`, `status` (completed/failed/needs_input), and bounded `summary`; reject extra keys, wrong IDs/SHA, invalid UTF-8, oversize/nonregular/symlink outputs and malformed JSON. A zero exit code alone is insufficient. Codex `--output-schema` and `--output-last-message` target the same run-bound schema; validate locally after exit. `completed` maps only to execution_completed when exit and cleanup succeeded and all provenance matches. Invalid output is failed; unresolved cleanup is unknown/cleanup failure, never success.

## Codex capabilities and process lifecycle

Construct an argument array from the installed executable using `exec --json --sandbox workspace-write --output-schema PATH --output-last-message PATH -C WORKTREE`. Use `--approve-for-me` only when explicitly enabled by saved installation policy. Do not use unsupported `--full-auto` or bypass flags. Existing authentication is preflighted without printing keys; do not choose a model. Official reference: [noninteractive mode](https://learn.chatgpt.com/docs/non-interactive-mode). Installed help establishes flag availability only, not successful authentication, resume or event interoperability.

Capability reports distinguish configured, executable/probed and actual verified execution. Resume is unsupported until an actual bounded resume round trip is verified and its exact binding documented; this milestone never auto-resumes unknown attempts. JSON event capture is private opaque data unless a versioned parser has an actual fixture and verified smoke run. Do not advertise events/resume on help output alone.

Add optional cancellation predicate and bounded polling (at most 250 ms while waiting) plus private bounded capture to `run_command`; preserve positional API and current default result shape/behavior. Timeout/cancel invokes existing process-tree termination and waits at most five seconds for the child; retain Windows Job close and POSIX group cleanup on every path. Failure to prove cleanup prevents a successful result. Worker death cannot promise descendant cleanup on all platforms: recovery fences the run and reports uncertainty rather than launching again.
