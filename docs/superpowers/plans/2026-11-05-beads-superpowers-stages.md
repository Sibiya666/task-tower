# Windows Beads / Superpowers stages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take authorized Windows Beads work through independently accepted SPEC, DEV and TEST in a bounded foreground session, preserving genuine native ownership, process and source evidence.

**Architecture:** A fixed Beads port extends admission with native claim, conservative postclaim eligibility and verified history. A separate role wrapper owns approved invocation, isolation and host provenance; an in-memory foreground coordinator orders these operations and hands off candidates without implementing PR/main acceptance. Beads remains the sole durable task/dependency/history authority.

**Tech Stack:** Python 3.11+ standard library, installed Windows Beads CLI, Git, existing `processes.run_command` / `WindowsJobProcess`, explicitly qualified installed role profile and pinned Superpowers instructions.

**Spec:** [Windows Beads / Superpowers stage coordination](../specs/2026-11-05-beads-superpowers-stages-design.md). Read repository AGENTS, [admission](../../beads-admission.md) and [backlog](../../backlog.md) first. The coordinator reports independent design approval; this plan does not itself grant real harness launch permission.

## Global Constraints

- Windows only; no installation, model, account, auth, scope or global harness configuration change.
- Beads/Dolt remains the sole task, dependency, claim and history authority. No replacement queue, SQL, database access, stage journal, durable scheduler, stage subissue graph or old-controller/profile adoption.
- Six fresh role instances: SPEC author, SPEC acceptor, DEV implementer, DEV acceptor, TEST executor, TEST acceptor. All acceptors are distinct from all executors and other acceptors; each actual call has a fresh process/context and attempt identity.
- Two task slots, two active supervised role/check processes, one active role per task, serialized Beads writes; these are fixed **interim** `.2` ceilings. `.4` owns configurable capacity/budgets/health and use of approved available capacity.
- 30 seconds per admission/Beads operation, 10 seconds per local Git operation, 30 minutes per role attempt, eight hours per foreground session, 8 MiB captured prefix per stream, 64 KiB request/result/event JSON, five-second cleanup deadline, at most one correction per stage per session.
- Native five-minute leases require 60-second renewal for current-session live claims on the serialized coordinator lane, with deadline priority and conservative monotonic expiry/cleanup reservation. Unknown renewal/readback, ownership loss or expiry cancels owned processes and fences without retry/revival. Cancellation callbacks read memory only; no Beads/Git/database/subprocess work in them. Heartbeats are native ephemeral liveness, not durable stage history; `.4` retains configurable health/capacity.
- Preserve every existing security predicate, assertion and timeout. Case-insensitively strip `GH_TOKEN`/`GITHUB_TOKEN`; children also receive no Beads credentials/directory, host evidence write access or private configuration.
- Unknown claim/write/launch/completion/cleanup/history outcome has no automatic replay, retry, release or reassignment. Never unclaim, force ownership, adopt a PID from JSON/history, resume an old claim or replay historical pilots.
- `candidate_for_integration` is not accepted/done/closed. A candidate retains its slot; the `.3` integration barrier is unavailable and fails closed. No `done:true` file, native closed label or model result releases a slot.
- `.3` PR/main/closure, `.4` configurable budgets/health, `.5` recovery, `.6` systematic fault qualification and `.7` full pilot remain separate. This increment still requires its own actual positive native six-role qualification before delivery/closure.

## Review Focus

- A dependency/gate changes after readiness or claim: refuse effects using the qualified native postclaim contract; unknown complex semantics are unsupported, never interpreted as an empty blocker list (Task 2).
- A structurally valid copied/stale verdict is returned by a real process: bind host-observed instance, exact inputs/source/artifacts and independently hash actual files before any stage advances (Task 3).
- A read-only role or TEST sandbox can write candidate/host evidence through a linked path: containment must prevent access, and host rehash must detect unexplained mutations (Task 3).
- A completed candidate or forged handoff file appears to free a slot: keep it occupied and refuse further dispatch beyond two until the actual integration/disposition authority exists (Task 4).
- The supervisor dies or a grandchild holds a stream open: native Windows tests must prove descendant death and actual EOF; a simulated cleanup receipt is insufficient (Task 3).
