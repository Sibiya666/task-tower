# Development roadmap

Backlog structure: large features are parent Issues with native sub-issues; milestones represent implementation stages or releases. These are independent relationships: a feature can span stages. The bookshelf projects them into the Tasks book, while Ideas retains proposals and the Project library links their Markdown artifacts. See [bookshelf hierarchy and current limits](github-books.md#target-bookshelf-hierarchy). Issue #13 is the overarching autonomous-development initiative; its existing child work remains traceable rather than being recreated. Issues #22/#23 must preserve native hierarchy and stage membership in the books.

The native development epic is [Issue 13](https://github.com/Sibiya666/task-tower/issues/13). Issues are the task source; this page records ordering and capability boundaries. The existing independent PR acceptor and the current chat's manual orchestration do not constitute a background development executor or automatic PR intake service.

[24 — project onboarding](https://github.com/Sibiya666/task-tower/issues/24) and [14 — dispatcher](https://github.com/Sibiya666/task-tower/issues/14) passed exact-main acceptance and automatic closure. Current parallel work is [15 — executor](https://github.com/Sibiya666/task-tower/issues/15) and [22 — session capture](https://github.com/Sibiya666/task-tower/issues/22), with separate worktrees and independent acceptance. This change implements capture/migration; its own exact-main acceptance and automatic closure are still required. Follow [continuous parallel process](development-process.md): refill up to two authorized independent Issues without a prompt, but serialize integration. Active-chat coordination is not a persistent execution pool.

The following implementation stages use native GitHub milestones: [MVP](https://github.com/Sibiya666/task-tower/milestone/1), [Night pilot](https://github.com/Sibiya666/task-tower/milestone/2), and [Harness and interface](https://github.com/Sibiya666/task-tower/milestone/3). Implemented foundations include the Codex observer overlay, readiness audit, interactive harness bootstrap, private connections/CLI and HTML books, and postmerge acceptance/publication paths. Project-first onboarding is accepted; a code path is not evidence of deployed runners, a continuously running synchronizer, or night readiness. The foreground dispatcher is documented in [dispatcher operations](dispatcher.md); the foreground development executor (#15) is documented in [executor operations](executor.md) and is under final acceptance. Independent stages (#16), automatic PR handling (#17) and daemon orchestration remain planned.

The architecture's target design remains in [the architecture spec](superpowers/specs/2026-11-01-agent-development-architecture-design.md); current onboarding requirements are in [the accepted spec](superpowers/specs/2026-11-01-project-onboarding-design.md). Native Issue dependencies, Project membership/status and milestones must be reconciled without replacing historical descriptions or acceptance evidence.

Session capture and provenance-only legacy migration are documented in [capture operations](session-capture.md). Native relationships are exposed in structured data; overlay hierarchy remains #23. This integration also forwards existing host authentication to the dispatcher proof source; it does not alter proof requirements or grant credentials to model processes.

The executor provides local durable admission, bounded isolated foreground attempts, cancellation and fenced recovery. A validated execution result never closes an Issue. Real installed Codex scratch execution is recorded separately from fixture transport tests; persistent automatic refill and stage/merge orchestration remain #16/#18/#19 and #17.
