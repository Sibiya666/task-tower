# Windows: наблюдение готовности Beads

Компонент `tt-auq.1` проверяет один явно разрешённый локальный источник и формирует пакет закреплённых входов. Он не занимает задачу, не запускает harness, не управляет этапами и не закрывает карточки. Живой допуск и атомарный claim через Beads относятся к `tt-auq.2`.

## Отдельное разрешение оператора

Конфиг книжек `TASK_TOWER_BEADS` разрешает отображение, а не выполнение. Для наблюдения готовности нужен отдельный приватный JSON. Пример иллюстрирует форму; подставьте существующие абсолютные пути, свой логический project ID, настоящий полный SHA исходников и разрешённые Beads ID. Не сохраняйте файл в репозитории и не передавайте его модели.

```json
{
  "version": 1,
  "executable": "C:/Private/beads/bd.exe",
  "projects": [{
    "id": "task-tower",
    "repository": "Sibiya666/task-tower",
    "directory": "C:/Private/beads/task-tower",
    "source": "C:/Projects/task-tower",
    "expected_head": "0123456789012345678901234567890123456789",
    "allowed_beads": ["example-task"]
  }]
}
```

```powershell
python -m task_tower.beads_admission --config C:/Private/admission.json --project task-tower --bead example-task
```

Требуются Windows, установленный `bd.exe`, embedded Beads и чистый локальный Git checkout на указанном SHA. Другие репозитории, sparse/partial checkout, submodules, внешние Git filters, config includes и расширение worktreeConfig не поддерживаются этим ограниченным компонентом. Системный и глобальный Git config отключены только для дочерних процессов; существующие пользовательские настройки не меняются. Поэтому checkout, чистота которого зависит от глобальных настроек конвертации, может получить отказ. Конфигурация не меняет модель, учётную запись, авторизацию или scopes. Вызовы фиксированы, без shell и сетевых запросов; один бюджет наблюдения — 30 секунд.

Индекс с `assume-unchanged` или `skip-worktree` тоже получает отказ: эти флаги могут скрывать изменения отслеживаемых файлов от `git status`. Компонент сам не сбрасывает флаги и не исправляет checkout.

## Как читать результат

Публичный пакет `beads.admission.observation` содержит квалифицированный ID `repository:beads:project:bead`, отдельные UUID наблюдения, закреплённые source HEAD/tree и хеши входов/политики, время и очищенные факты завершения процессов. Пути, конфиг, task prose, raw stdout/stderr и окружение в пакет не входят.

| Исход | Код завершения | Значение |
| --- | --- | --- |
| `eligible_observation` | 0 | Задача наблюдалась готовой, незанятой и разрешённой при закреплённых входах |
| `refused` | 2 | Известное несоответствие: например, задача занята, не готова, источник изменён или не разрешён |
| `unknown` | 3 | Получить проверяемый результат не удалось, в том числе неизвестно завершение/очистка процесса |

Пакет может устареть сразу после чтения. Даже успешный результат не доказывает владение задачей: перед эффектами будущий координатор повторяет проверки и выполняет атомарный claim через Beads под настоящим actor. Совпадение JSON или хешей не восстанавливает процесс, claim либо fence. Книжки сохраняют read-only интерфейс.

## Контракт будущих доказательств этапов

Будущий envelope включает schema/kind, квалифицированный ID задачи, разные run/attempt ID, stage (`spec`, `development`, `test`, `pr`, `main`), actor, закреплённые input/policy/source digest, подлинные process facts, относительное имя артефакта и SHA256. Для независимой приёмки нужны отдельная личность reviewer и точные head/base PR; изменение любого из них инвалидирует verdict.

Это словарь и структура, а не готовое доверенное хранилище доказательств. Валидный envelope и вывод модели не подтверждают происхождение или приёмку. `execution_completed` означает завершение исполнения; `accepted`/`done` требуют независимых барьеров и принятого main. Неизвестные cleanup/source/review остаются неизвестными. Старые receipts и claims не импортируются в новый процесс.

## Границы проверки

Тестовые ready/show ответы, включая схему официального Beads с отсутствующим assignee, помечаются как fixtures. Проверка отказа на реально занятой карточке не является успешным живым запуском агента. Полный цикл и пилот относятся к следующим задачам цепочки. Закрытие канонической карточки координатором после принятого main не означает поставленную автоматизацию Beads-close.
