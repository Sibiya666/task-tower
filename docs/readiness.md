# Task Tower

Общая система агентной разработки с Superpowers, очередями и независимой приёмкой. Архитектура: [спека](superpowers/specs/2026-11-01-agent-development-architecture-design.md). Реализован первый этап — CLI проверки готовности проекта. Очередь агентов, модельное исполнение, слияния и книги пока не реализованы.

## Запуск

Python 3.11+ и Git; сторонние зависимости не нужны. Из корня репозитория:

```powershell
python -m unittest discover -s tests -v
python -m task_tower audit --project C:/path/to/dialoid --manifest examples/dialoid.project.json --output ../runtime/dialoid-readiness.json
```

Аудит проверяет корень Git, HEAD, чистоту рабочей копии (включая неотслеживаемые файлы), наличие обязательных документов, указанного файла Superpowers и исполняемых инструментов. Он не запускает команды манифеста, не обращается к моделям и не меняет целевой проект. Git использует `GIT_OPTIONAL_LOCKS=0`. Содержимое skill фиксируется SHA-256; наличие файла не доказывает соблюдения методологии агентом.

Манифест — доверенная исполняемая конфигурация. Перед использованием настройте его под проект и проверьте команды. Пример Dialoid намеренно не устанавливает Superpowers: путь к skill должен указывать на реальный файл внутри проекта. Присутствие `.superpowers/` с рабочими артефактами не означает, что навыки установлены. Пример содержит только проверки ядра; он не подтверждает готовность игры, Godot или UI.

Чтобы явно выполнить tool probes и baseline-команды на чистой копии:

```powershell
python -m task_tower audit --project C:/path/to/clean-dialoid --manifest examples/dialoid.project.json --run-checks --output ../runtime/dialoid-baseline.json
```

`--run-checks` исполняет команды с правами текущего пользователя. CLI ограничивает время и жизненный цикл процессов, но сам не создаёт файловый или сетевой sandbox. Запускайте проверки в подготовленной изолированной среде. Зависимости должны быть подготовлены заранее: пример использует `--no-restore`. Команды идут последовательно; первая ошибка или изменение проекта останавливает выполнение. Генерируемые тестами файлы должны быть корректно исключены Git.

В Windows процесс создаётся приостановленным, включается в Job Object и только затем запускается. Закрытие Job Object завершает потомков даже после раннего выхода родителя; ошибка настройки блокирует запуск. В POSIX используется отдельная группа процессов (процесс, который намеренно отделился через setsid, находится вне этой гарантии; эта платформа не проверена в текущем пилоте). Это управление временем жизни, не граница безопасности против недоверенного кода.

## Отчёт и коды выхода

- `blocked`: не выполнены условия среды или проверки, код 1.
- `awaiting_baseline`: аудит прошёл, baseline ещё не запускался, код 0.
- `ready_for_pilot`: команды прошли на неизменившейся чистой версии, код 0. Это готовность среды к контролируемому пилоту, не доказательство работоспособности агентного исполнения.
- Невалидный ввод или ошибка записи отчёта: код 2, сообщение в stderr.

`night_ready` и `agent_execution_verified` всегда `false` в этом этапе. CLI ещё не проверяет доступ к модели, бюджет, полный набор сценариев, полномочия приёмщиков или восстановление main. Не используйте один код 0 как разрешение автомержа.

JSON содержит commit SHA, хеш манифеста и skill, окружение хоста, статусы команд, коды выхода, время, размеры и SHA-256 stdout/stderr. Сырые потоки временные и удаляются: их хеши дают идентичность вывода, но не заменяют сохранённые доказательства приёмки будущих этапов. Аргументы команд входят в отчёт — не передавайте в них секреты. Вывод команд не попадает в JSON. Отчёт сохраняется вне проверяемого проекта, чтобы не загрязнять и не перезаписывать его файлы.
