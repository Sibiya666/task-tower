## AgentsRoom документирует граф ролей и desktop-расписания

Документация multi-project описывает проекты, роли, состояния, отдельные CLI/PTY, сохранение сессии при переключении проекта, просмотр изменений и optional worktrees. Она также допускает получение контекста других проектов аккаунта. Поэтому удобство разделения в интерфейсе нельзя считать гарантией конфиденциальности между проектами. ([Multi-project / multi-agent](https://agentsroom.dev/features/multi-project-multi-agent))

**Teams документирует переходы между ролями, structured handoff, параллельные проверки и join, ограниченные циклы и восстановление состояния.** Exit code проверочной команды может переопределить самоотчёт агента; entry check способен не допустить запуск. Документированы review-режимы с CLI-ограничениями. Relay использует одну сессию для смены ролей, team — отдельные сессии; сам поставщик признаёт, что relay не даёт независимого второго мнения. При достижении max-cycles требуется решение человека. Это существенное пересечение с задачами stage-controller, хотя описанное поведение ещё не проверено в Task Tower. ([Agent Teams](https://agentsroom.dev/features/teams))

Расписания срабатывают в открытом desktop-приложении и могут догонять пропущенный слот после его возврата; это не свидетельство постоянно работающего сервера. Документированы история, запуск команды/агента и настройки permission mode. Windows x64/ARM64 installers и 64-битная Windows заявлены поставщиком; прочитанные страницы не устанавливают минимальную версию ОС или требуемые гарантии Codex isolation на Windows 10. ([Scheduled Tasks](https://agentsroom.dev/features/scheduled-tasks), [Download](https://agentsroom.dev/download), [Windows announcement](https://agentsroom.dev/blog/agentsroom-now-on-windows))

| Область сравнения | Что документировано или полезно как референс | Что остаётся неизвестным для Task Tower |
| --- | --- | --- |
| Работа по проектам | Визуальные проекты, агенты, состояния и PTY | Изоляция приватных данных, соответствие UI фактам EOF/cleanup |
| Этапы и проверки | Граф Teams, handoff, check exit code, ограниченные циклы | Соответствие обязательным шести ролям, независимость конкретных доказательств |
| Продолжение | Desktop schedules и восстановление Teams state | Atomic Beads claim, fencing, unknown-outcome recovery внешних эффектов |
| Код и приёмка | Просмотр изменений, optional worktree, review nodes | Exact head/base approval, текущий CI, serialized main acceptance и canonical closure |
| Windows | Установщики и поддерживаемый CLI | Нативная Windows 10 квалификация, приватность Beads DB и descendants cancellation |

Это перечень непроверенного, **не утверждение об отсутствии функций**. Отдельные терминал, ветка, сессия и read-only режим — разные свойства; их наличие не доказывает запрет доступа к чужим данным. При дальнейшем сравнении нужно проверять именно эти контракты, сохраняя Beads как источник задач. AgentsRoom не является вариантом внедрения: пользователь выбрал собственный Task Tower. Сравнение ограничено функциями, UX и различиями контрактов.

## Первичная статья OpenAI помогает отделить метод от backend

Habr-страница помечена переводом и ссылается на Ryan Lopopolo/OpenAI; она не является независимым повторным подтверждением исходного кейса. ([Habr](https://habr.com/ru/companies/otus/articles/1009342/))

Первичный материал от 11 февраля 2026 описывает внутренний эксперимент: краткий AGENTS как навигацию, структурированные знания и планы, доступную агенту наблюдаемость и механические архитектурные ограничения. Урок для этого анализа — при отказе искать недостающую возможность и проверяемый контракт, а не просто увеличивать число попыток. Политика merge gates и оценка скорости относятся к описанному кейсу; их нельзя переносить на Task Tower как универсальную норму или основание принять красный CI. Статья не поставляет Windows sandbox, task engine или доказательство шестиролевой готовности. ([OpenAI: Harness engineering](https://openai.com/index/harness-engineering/))

Наша рекомендация из сопоставления источников — дать актуальному entrypoint текущий task, source SHA, принятую границу и ближайшее решение; для каждого отказа отдельно записывать факт, интерпретацию, недостающее evidence и ограниченный следующий опыт. Это аналитический вывод, а не дословное правило статьи и не доказанная причина всех прошлых ошибок. Ближайший архитектурный выбор должен сравнить сохранение, упрощение и адаптацию существующих частей на конкретном пользовательском сценарии, без заранее выбранного нового framework.

## Три значения harness нельзя объединять в одну замену

Harness engineering в статье — метод организации работы; Harness² — конкретный исследовательский алгоритм оптимизации окружения; Task Tower adapter — граница запуска, полномочий и доказательств. Выбор одного не решает автоматически задачи остальных. [Трассировка Harness²](harness2/01-architecture-and-gap-map.md), [аудит пяти подсистем](harness-engineering/01-five-subsystems-audit.md) и [разбор направления](2026-11-05-direction-review.md) сохраняют эти различия.

После расширенной оценки текущей и целевой архитектуры новый бэклог будет составляться совместно с пользователем. Эти черновые материалы не разрешают автоматическое продолжение старой цепочки, merge/closure исследовательских детей, замену Beads/Superpowers, новые credentials, ACL или снижение обязательной приёмки.
