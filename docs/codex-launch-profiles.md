# Профиль запуска Codex: что должен передавать Task Tower

2026-11-06, Europe/Moscow. Продолжение [первой проверки локального запуска](local-codex-launch-proof.md). Данные получены на установленной `0.166.0-alpha.6`, SHA256 `925c7d0665ffa49b0dcf748e034a805a04da984164ac92301432073b47789b99`; это исследование интерфейса и ограниченные реальные опыты, не поставленный dispatcher или кнопка башни.

## Итог

Локальный клиент способен не только создать persistent-сессию и выполнить чтение, но и создать проверяемый файл в выбранном worktree. Для этого параметры **новой** сессии заданы явно в пределах текущего разрешения вызывающего чата: `:workspace`, `on-request`, `auto_review`, один workspace-root. Глобальные настройки, ACL, аккаунт, авторизация и установка клиентом не менялись. Модель не переопределялась; сервер вернул прежний default `gpt-6-astra`.

Это не изменение старой read-only сессии и не автоматическое копирование неизвестного Desktop-профиля. Основание допуска — текущее доверенное разрешение вызывающего чата на workspace-write/auto_review в проекте; каталог доступных профилей сам по себе такого разрешения не даёт. Worktree находится внутри уже разрешённого корня проекта; у sandbox инструментов `networkAccess=false`; это не утверждение об offline-доступе модели или MCP startup.

## Минимальный контракт для тонкой связки

Task Tower должен хранить отдельный **допуск запуска проекта**, а не пытаться угадать состояние Desktop по каталогу профилей. Такой допуск выбирает или наследует проверяемые параметры внутри уже выданных пользователем полномочий: repository/worktree, существующий permission-profile ID, approvalPolicy, approvalsReviewer, runtimeWorkspaceRoots, настройки модели/effort и источник их актуальности. Если доступна только последняя сохранённая metadata, это должно быть видно; её нельзя называть текущим выбором активного writer.

Порядок запуска: прочитать доступные профили и требования → сопоставить выбранный допуск с исходным grant → проверить readiness без setup → создать thread → проверить **возвращённые** cwd/model/profile/policy/reviewer/roots/network → только затем отправить задачу. Отсутствие, устаревание или расширение обязательного параметра останавливает именно запуск. Структура допуска не создаёт вторую очередь задач и не заменяет Beads claim.

Для approvalPolicy и reviewer нужны отдельные поля. `on-request` с reviewer=user требует реального пользовательского решения, а не автоматического accept от Task Tower. При существующем auto_review решение делегируется штатному механизму Codex в рамках разрешённого режима; семантическая независимая приёмка результата и PR/main остаётся отдельной. Нельзя превращать одно разрешение в `acceptForSession`, execpolicy/network amendments или blanket approval без соответствующего основания.

При запросе пользователя клиент связывает pending request с session/turn/item и показывает точную операцию. Ответ отправляется только для ещё актуального запроса; затем проверяется и `serverRequest/resolved`, и фактический outcome соответствующего item. UI-флаг «ответ отправлен» не равен «команда выполнена». При неизвестном исходе хранится попытка и проводится сверка, а не новый запуск задачи.

Следующий инженерный шаг — небольшой локальный adapter с этим контрактом и явной обработкой requested/declined/completed/unknown. Только после его независимой проверки следует подключать существующие admission/Beads claim и кнопку башни. В этих опытах они не реализовывались; отдельная очередь, новый task engine и старый conveyor не создавались.

Официальные первоисточники для сверки смысла API: [App Server](https://learn.chatgpt.com/docs/app-server), [permission profiles](https://learn.chatgpt.com/docs/permissions), [permission modes](https://learn.chatgpt.com/docs/permission-modes). Актуальная документация не заменяет сгенерированную alpha6-схему и фактические receipts. При публикации этого отчёта действуют свежая whole-PR приёмка точных head/base, настоящий применимый CI, expected-head merge и независимая exact-main приёмка.
