# Продукты агентной разработки

Исследовано 2026-11-01. Это сравнение документированных функций, а не независимый замер эффективности. Наша база — docs/superpowers/specs/2026-11-01-agent-development-architecture-design.md.

## Что уже предлагают готовые системы

### Takeaway
Наш общий поток «задача → агент → проверки → PR» уже существует у нескольких поставщиков. Отличие нашей архитектуры — персональный интерфейс башни, единый процесс Superpowers и явная приёмка каждого этапа; эти отличия пока не доказаны как улучшение качества или стоимости.

### Cited Findings
- Devin имеет REST API для интеграций и автоматизаций. Текущая API v3 разделяет организационные ресурсы (сессии, knowledge, playbooks, secrets) и enterprise-управление; service users поддерживают роли и аудит. Старые v1/v2 находятся в периоде вывода и не получают новые возможности. Значит, адаптер по старому примеру API рискует устареть ещё до пилота. — [Devin API Overview](https://docs.devin.ai/api-reference/overview)
- Cursor Cloud Agents запускают задачи из web, IDE, CLI, API, Slack и связанного issue/PR. Каждый агент получает изолированную VM, а состояние разговора и артефакты сохраняются отдельно от неё. Документированный путь заканчивается веткой и PR для человеческого ревью. Терминальные команды выполняются автоматически; поставщик отдельно описывает сетевые ограничения и защиту секретов. — [Cursor security overview](https://prod.cursor.com/docs/cloud-agent/security)
- Cursor предлагает API запуска и управления агентами и окружениями; создание PR — параметр запуска. Существуют ограничения частоты и числа параллельных сборок. Это программируемый исполнитель, который можно подключать к своему таск-менеджеру. — [Cloud Agents API](https://prod.cursor.com/docs/cloud-agent/api/endpoints)
- С 28 октября 2026 GitHub описывает новую cloud-схему Copilot для платных планов. Она отделяет клиент, сессию и окружение, поддерживает перенос сессии между клиентами. GitHub различает Actions-based исполнение и cloud sandbox: у них разные сроки хранения, настройка окружения и границы репозиториев. Старое ограничение «один репозиторий» относится к Actions-based пути, а cloud sandbox может менять несколько репозиториев организации. — [Copilot on GitHub.com and GitHub Mobile](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)
- Factory предоставляет scheduled, Slack, GitHub и webhook-автоматизации, run identity и целевую машину. В каталоге есть Ticket to PR: периодический подбор готовых задач Linear/Jira по одной до открытого PR; есть CI triage и утренний дайджест. Webhook-возможности зависят от доступности в организации. — [Factory Custom Automations](https://docs.factory.com/automations/custom)
- Factory Missions описывает декомпозицию в milestones, оркестрацию работников, проверки и использование существующих skills/MCP/hooks. Поставщик сам называет нерешёнными вопросы пользы параллельности и баланса стоимости/качества; наличие оркестратора не доказывает преимущество многоагентности. — [Factory Missions](https://docs.factory.com/missions/overview)

### Inferences
- Строить собственные API сессий, облачные машины, снимки окружения и доставку PR с нуля для первого пилота не нужно. Наш слой может отвечать за задачи, правила Superpowers и отображение, используя готовый исполнитель.
- Предварительный выбор Vikunja был преждевременным: сначала следует выбрать систему исполнения и проверить, какая готовая интеграция сокращает работу. Если код и приёмка уже живут в GitHub, дополнительный таск-трекер может создать лишнюю синхронизацию. Vikunja остаётся разумным выбором только если независимая общая книга важнее нативного workflow.
- Автоматическое слияние после агентной приёмки — более сильная автономность, чем документированный базовый путь Cursor. Это наше сознательное решение с дополнительными требованиями к проверкам, а не стандарт, доказанный рынком.

### Gaps
- Без пробного запуска нельзя сравнить качество на Dialoid, фактические расходы и соблюдение Superpowers.
- Не проверялись цены и доступность аккаунта владельца. API и enterprise-функции могут не входить в имеющуюся подписку.
- Описание функции в документации не является доказательством надёжности, частоты успешных слияний или экономии времени.

## Чего не хватает нашей спецификации

### Takeaway
Самый крупный пробел — подготовка проектов к автономной проверке: мы подробно описали роли, но недостаточно определили рабочее окружение и наблюдаемые доказательства результата.

### Cited Findings
- Cursor описывает окружение как набор репозиториев, зависимостей, инструментов, секретов, startup-команд и сети. Поддерживаются снимки/сборки и Dockerfile-конфигурация; multi-repo окружения позволяют тестировать согласованные изменения. Конфигурация и готовая сборка используются повторно. — [Cursor environment setup](https://prod.cursor.com/docs/cloud-agent/setup)
- Devin запускает свежую копию подготовленного snapshot; изменения сессии не изменяют базовый снимок. Blueprint задаёт воспроизводимое окружение, а секреты задаются отдельно. Доступ к SCM требуется подготовить до запуска. — [Devin environment setup](https://docs.devin.ai/onboard-devin/environment)
- Factory каждый параллельный запуск создаёт как отдельный экземпляр от готового снимка. Несохранённые изменения одного экземпляра не видны другому; долговечные результаты нужно публиковать отдельно. Параллельность ограничена compute, доступами и лимитами моделей. — [Factory environments](https://docs.factory.com/environments/run-droids)
- Devin имеет отдельный E2E workflow: запускает приложение, формирует тестовый сценарий, взаимодействует через браузер и прикладывает запись. Документация прямо ограничивает такую запись короткой проверкой основного сценария и рекомендует CI/тестовые наборы для полного покрытия. Накопленные способы проверки можно превращать в skills через PR. — [Devin testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings)
- Devin рекомендует конкретные границы, критерии результата, ссылки на примеры и код, а также циклы unit/integration, lint и static analysis. Review Auto-Fix описан как путь исправления замечаний и CI до merge-ready состояния. — [Instructing Devin](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)

### Inferences
- В спеку нужен «контракт готовности проекта»: чистый checkout → установка → запуск → тест → пользовательский сценарий. Включить тестовые данные, зависимости, секреты, разрешённые сети, время и ресурсы. До его прохождения проект не допускается к автономной ночной работе.
- К каждой приёмке прикладывать не только текст агента, но и машинные результаты: CI run, exit codes, тестовые отчёты, скриншоты/видео для UI, commit SHA и версию окружения. Приёмщик анализирует доказательства; не заменяет тестовый стенд.
- Нужен жизненный цикл окружений: создание, предварительный health-check, очистка, восстановление, изменение версии. Worktree изолирует файлы Git, но не порты, процессы, БД, кэши и внешние сервисы.
- Приёмка после main проверяет интеграцию кода, но не доказывает успешный релиз. Отдельно решить, входит ли deployment/staging smoke в определение готовности и кто наблюдает регрессии после выпуска.
- Полезна версионируемая библиотека project skills: обнаруженные при работе инструкции добавляются через проверяемые PR, а не бесконтрольно в память постоянного агента.
- Дополнение владельца о третьей книге «Библиотека проекта» полезно для обнаружения контекста. Её лучше сделать индексом канонических MD в репозитории: тип артефакта, статус (черновик/принят/заменён), владелец решения, связи с задачами и commit SHA. Содержимое не копируется в ещё одно хранилище. Агент должен находить действующую спеку, отличать её от отменённой и ссылаться на версию, по которой работал; одна красивая коллекция ссылок этого не гарантирует.

### Gaps
- Не исследовано реальное окружение Dialoid и наличие CI/E2E; эти требования — обнаруженные области проверки, не утверждение об отсутствии тестов в проекте.

## Что стоит изменить в последовательности работ

### Takeaway
Первой целью должен быть измеримый автономный проход одной небольшой задачи; постоянные команды и глубокий рескин стоит строить после доказательства этого цикла.

### Cited Findings
- Factory требует для надёжной валидации Missions автоматизированный способ упражнять приложение как пользователь, с запуском или имитацией зависимостей. Простой задаче рекомендует обычную сессию; отдельно предупреждает, что Missions не являются fire-and-forget. — [Factory Missions](https://docs.factory.com/missions/overview)
- У GitHub окружение, контекст сессии и долгосрочная память — разные понятия. Это согласуется с нашим правильным разделением задачи, сессии и агента и не требует бессрочно живущего ведущего процесса. — [GitHub cloud model](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)

### Inferences
- Группы следует моделировать как маршрутизацию по зонам ответственности и набор разрешений/skills, а не как постоянный штат процессов. Запускать нужные роли под задачу.
- Не делать одинаковый тяжёлый pipeline для опечатки и изменения схемы БД. Superpowers остаётся основой, но строгость приёмки и разрешение auto-merge задаются классом риска.
- Для пилота достаточно одного исполнителя, одного независимого ревьюера и объективных CI/E2E gates. Дополнительные приёмщики вводятся только если измеримо находят пропущенные дефекты.
- До усложнения зафиксировать метрики: доля задач без вмешательства, стоимость принятого результата, время до main, число возвратов, регрессии/откаты, доля ночных блокировок. Без них нельзя отличить реальное улучшение от красивого движения персонажей.
- Рекомендуемый порядок: аудит готовности Dialoid → несколько ограниченных задач через готовый runner → измерение и исправление сбоев → тонкий сервис очереди → книга/башня → параллельные группы и новые проекты.

### Gaps
- Нет проверенного рынка числа «правильных» агентов или обязательной организационной структуры. Роли — проектная гипотеза, которую нужно проверять экспериментом.
